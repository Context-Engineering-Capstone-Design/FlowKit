# AI 기능명세서와 현재 코드베이스의 충돌 정리

이 문서는 임시 문서다. 아래 항목을 모두 해결하면 파일과 `충돌사항/` 폴더째로 지운다. 그래서 다른 문서에서 이 문서를 링크로 걸지 않는다.

기준 시점의 코드는 `backend/app/services/`와 `modeling/`이다.

---

## 1. 답변을 다시 만들면 적용 Context가 사라진다

**충돌 대상:** AI-ANSWER-004, BE-AIRESP-003, NFR-011

**현재 동작**

`backend/app/services/ai_response_service.py`의 `send_message`는 적용 Context가 있으면 이전 대화 흐름을 비우고(78행) Context만 근거로 답을 만든다(87행). 그런데 같은 파일의 `regenerate`는 적용 Context 자리에 빈 목록을 넘기고, 대신 앞선 대화 흐름 전체를 넘긴다(145행).

**무엇이 문제인가**

처음 답변과 다시 만든 답변의 입력 조건이 서로 다르다. Context를 골라 물어본 답변을 다시 만들면, 사용자가 고르지 않은 대화까지 근거가 되고 정작 고른 Context는 빠진다. 사용자는 같은 질문의 두 답변을 버전으로 비교한다고 생각하지만 실제로는 조건이 다른 두 답변을 비교하게 된다. "Context가 적용된 상태에서 AI는 적용된 Context를 우선 기준으로 답해야 한다"는 NFR-011에도 어긋난다.

**해결 방향**

`BE-CTXAPPLY-003`이 적용 Context 사용 이력을 이미 저장하고 있으므로(`context_service.save_log` 호출), 재생성 시 그 이력을 다시 읽어 원래 입력 조건을 복원해 넘긴다. 이력이 없는 답변만 지금처럼 대화 흐름 기준으로 처리한다.

**우선순위:** 상. 기능이 없는 것이 아니라 이미 잘못 동작하고 있는 항목이다.

---

## 2. 모델을 하나만 쓰도록 고정되어 있다

**충돌 대상:** AI-CORE-001, AI-CORE-002, AI-CORE-003, REQ-056, NFR-017, BE-INPUT-005, BE-INPUT-006

**현재 동작**

`modeling/config.py`에 모델명이 하나만 상수로 박혀 있다(7행). `modeling/llm.py`의 `get_chat_model`은 모델명을 인자로 받긴 하지만(36행), 어떤 모델이 쓸 수 있는 모델인지 판단할 목록이 없다. `modeling/types.py`의 `AnswerRequest`에는 모델 선택값을 담을 자리가 없고(37~46행), 백엔드의 `send_message`, `regenerate`, `_call_refiner` 어디에도 모델 인자가 없다.

**무엇이 문제인가**

사용자가 모델을 고를 수 있어야 한다는 요구사항을 지금 구조로는 충족할 수 없다. 백엔드가 모델 선택값을 받아도 모델링 파트로 넘길 통로가 없다.

**해결 방향**

모델 목록을 상수로 정의하고, 선택값을 검증해 실제 모델을 정하는 단계를 만든다. `AnswerRequest`와 정제 호출에 모델 선택값을 받는 자리를 만들고, 백엔드 전송·재생성·정제 흐름에서 그 값을 이어 넘긴다.

**우선순위:** 중. 요구사항 우선순위는 "하"지만, 아래 3번과 4번이 모두 이 통로를 함께 쓴다.

## 3. 웹 검색을 수행하는 코드가 없다

**충돌 대상:** AI-SEARCH-001, AI-SEARCH-002, REQ-055, BE-INPUT-004

**현재 동작**

`modeling/` 전체에 검색 관련 코드가 없다. `AnswerRequest`에 검색 사용 여부를 담을 자리도 없다.

**무엇이 문제인가**

`BE-INPUT-004`는 "실제 웹 검색 수행은 AI 모델링/외부 검색 연동 책임"이라고 적혀 있는데, 받는 쪽이 비어 있다. 백엔드가 옵션을 검증해 넘겨도 아무 일도 일어나지 않는다.

**해결 방향**

모델에 내장된 Google 검색 도구를 붙이는 방식으로 구현한다. 별도 검색 서비스 계약이나 API 키 발급이 필요 없다. `AnswerRequest`에 검색 사용 여부를 받는 자리를 만들고, 켜진 요청에만 도구를 붙인 클라이언트를 쓴다.

**우선순위:** 하

---

## 4. 첨부 파일을 모델에 넘길 방법이 없다

**충돌 대상:** AI-ATTACH-001, AI-ATTACH-002, REQ-052, REQ-053, BE-INPUT-003

**현재 동작**

`modeling/types.py`의 대화 데이터는 모두 글자만 담는다. `ChatTurn.content`와 `AnswerRequest.user_prompt`가 문자열이고, 첨부를 담을 자리가 없다. 백엔드의 `_generate`도 글자만 조립해 넘긴다.

**무엇이 문제인가**

`BE-INPUT-003`은 첨부를 사용자 메시지와 연결하는 것까지 처리하지만, 연결된 첨부가 모델 입력으로 이어지지 않는다. 사용자는 이미지를 붙이고 질문했는데 모델은 이미지를 보지 못한 채 답하게 된다.

**해결 방향**

`AnswerRequest`에 첨부 목록을 받는 자리를 만든다. 이미지는 모델에 그대로 실어 보내고, PDF와 텍스트 계열 파일은 글자를 뽑아 질문 앞에 붙인다. 글자를 뽑지 못하는 파일은 오류로 알린다.

**우선순위:** 하

## 5. 모델 클라이언트 재사용 방식이 요청별 옵션과 맞지 않는다

**충돌 대상:** AI-CORE-003

**현재 동작**

`modeling/llm.py`의 `get_chat_model`은 모델명만으로 결과를 기억해 재사용한다(35~36행).

**무엇이 문제인가**

지금은 옵션이 없어 문제가 없지만, 위 2~4번을 넣으면 같은 모델 이름으로 서로 다른 설정의 클라이언트가 필요해진다. 웹 검색 도구를 붙인 클라이언트와 붙이지 않은 클라이언트가 대표적이다. 모델명만 기억 기준으로 쓰면 먼저 만들어진 하나가 계속 재사용되어, 검색을 켰는데 검색이 안 되거나 껐는데 검색이 도는 상태가 된다.

**해결 방향**

기억 기준에 요청 옵션을 함께 넣는다. `configure`가 기억을 비우는 처리도 그대로 유지한다.

**우선순위:** 중. 2~4번을 구현할 때 함께 처리해야 하며, 따로 두면 원인을 찾기 어려운 문제가 된다.

## 확인이 필요한 항목

아래는 충돌로 단정하지 않았다. 실제 API 키로 확인한 뒤 결론을 낸다.

### 다시 만든 답변이 이전 답변과 같을 수 있다

**관련:** REQ-049, AI-ANSWER-004

`modeling/config.py`에 적힌 대로 현재 모델은 샘플링 값을 고정으로 쓰며 값을 지정할 수 없다. 위 1번을 고쳐 재생성 입력을 원래 조건 그대로 맞추면, 같은 입력에 같은 답이 나올 가능성이 생긴다. REQ-049는 "재생성 실행 시 새 답변이 생성되고 응답 버전에 추가되어야 한다"고 정하고 있으므로, 답이 매번 똑같이 나오면 버전 이동 기능이 의미를 잃는다.

같은 입력으로 여러 번 호출해 답이 실제로 달라지는지 먼저 확인한다. 달라지지 않으면 다양성을 확보할 방법을 따로 정해야 한다.

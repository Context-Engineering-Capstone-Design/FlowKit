# FE 기능명세서와 현재 코드베이스의 충돌 정리

이 문서는 임시 문서다. 아래 항목을 모두 해결하면 파일과 `충돌사항/` 폴더째로 지운다. 그래서 다른 문서에서 이 문서를 링크로 걸지 않는다.

기준 시점의 코드는 `frontend/src/`다.

먼저 적어둘 것은, 이미 만들어진 부분은 대체로 명세와 잘 맞는다는 점이다. 인증과 토큰 재발급, 채팅·브랜치 관리, 블록 선택, Context 편집과 블록별 정제, AI 응답 관리는 요구사항대로 동작한다. 특히 정제 승인·거절이 한 방향으로만 처리되어, 프로토타입에 남아 있던 승인 취소 문제(`프로토타입_충돌_정리.md` 1·2번)를 코드는 이미 피해 갔다.

아래는 아직 없거나 어긋나는 항목이다.

---

## 1. 프로필 메뉴가 없어 계정·설정 기능 전체로 들어갈 길이 없다

**충돌 대상:** REQ-058, REQ-059, FE-AUTH-004, FE-AUTH-005

**현재 동작**

`Sidebar.tsx`의 `ProfileArea`는 아바타, 이름, 이메일과 '로그아웃' 글자 버튼만 한 줄로 놓여 있다. 누르면 바로 로그아웃된다. 팝업 메뉴가 없다.

**무엇이 문제인가**

REQ-058은 프로필 영역을 눌렀을 때 '사용자 정보', 'API 키 관리', '피드백 남기기', '로그아웃' 네 항목이 있는 팝업이 열려야 한다고 정한다. 지금은 팝업 자체가 없어서, 로그아웃을 뺀 나머지 세 기능은 화면에서 도달할 방법이 없다.

`api/auth.ts`에는 `fetchMe`와 `updateMe`가 이미 있는데 어느 화면도 쓰지 않는다. 통로만 없는 상태다.

**해결 방향**

프로필 영역을 누르면 열리는 팝업을 만들고 네 항목을 넣는다. 이 하나를 만들면 아래 2번 기능들의 진입점이 함께 생긴다.

**우선순위:** 상. 이것이 막혀 있어서 2번 전체가 도달 불가 상태다.

---

## 2. 사용자 설정(2.10)이 통째로 없다

**충돌 대상:** REQ-059, REQ-060, REQ-061, REQ-062, REQ-063, FE-AUTH-005, FE-USERSET-001~007, BE-USERSET-001~007

**현재 동작**

사용자 정보 모달, API 키 관리 모달, 피드백 모달이 모두 없다. 관련 화면 파일도 없다.

**무엇이 문제인가**

API 키를 등록할 방법이 없다는 점이 특히 걸린다. REQ-062는 키가 없는 상태로 메시지를 보내면 안내하도록 정하는데, 안내를 받아도 등록하러 갈 곳이 없다. 백엔드가 사용자 키를 요구하는 구성이라면 대화 자체가 막힌다.

**해결 방향**

1번의 팝업을 먼저 만들고, 사용자 정보 모달과 API 키 관리 모달을 잇는다. 피드백 모달은 그다음이다. 우선순위는 API 키 관리, 사용자 정보, 피드백 순이다.

**우선순위:** 상 (API 키 관리), 중 (사용자 정보), 하 (피드백)

---

## 3. 입력 보조(2.9)가 통째로 없다

**충돌 대상:** REQ-052, REQ-053, REQ-054, REQ-055, REQ-056, FE-INPUT-001~005, BE-INPUT-001~006

**현재 동작**

`ChatArea.tsx`의 `Composer`에는 입력창과 전송 버튼만 있다. 첨부 버튼, 웹 검색 토글, 모델 선택 버튼이 모두 없다.

**무엇이 문제인가**

요구사항 우선순위가 모두 '하'라서 당장 급하진 않다. 다만 AI 쪽 충돌 문서(`AI기능명세서/충돌사항/코드베이스_충돌_정리.md`)의 2·3·4번이 같은 기능의 서버·모델 쪽 미비를 지적하고 있다. 세 영역이 다 비어 있으므로, 구현할 때는 화면만 따로 만들지 말고 세 파트를 함께 잡아야 한다.

**해결 방향**

모델 선택을 먼저 한다. 요구사항(NFR-017)이 확장을 전제로 하고, AI 쪽에서도 모델 고정이 우선순위 문제로 올라와 있다. 첨부와 웹 검색은 그다음이다.

**우선순위:** 하. 단, 착수 시점을 AI·BE와 맞춘다.

---

## 4. 메시지 블록을 복사하거나 수정할 수 없다

**충돌 대상:** REQ-017, REQ-018, REQ-019, FE-MSG-005, FE-MSG-006, FE-MSG-007, FE-MSG-008, BE-MSG-004

**현재 동작**

`MessageBlockItem.tsx`의 동작 버튼은 AI 블록에만 있고, 좋아요·싫어요·답변 다시 시도·버전 이동뿐이다. 복사 버튼, 수정 버튼, 더보기 메뉴가 없다. 사용자 블록에는 동작 버튼이 하나도 없다.

**무엇이 문제인가**

REQ-018(메시지 수정)은 우선순위 '중'이고, 서버에는 `BE-MSG-004`로 수정본 저장 기능이 이미 정의되어 있다. 화면만 없다.

여기에 딸린 문제로, 버전 이동 영역이 AI 블록에만 그려진다. 사용자 블록은 수정을 통해서만 버전이 생기는데 수정 기능이 없으니 지금은 드러나지 않지만, 수정을 붙이면 사용자 블록의 버전 이동도 함께 필요하다.

**해결 방향**

블록 더보기 메뉴를 만들어 복사·직접 수정·여기서 브랜치 생성을 넣는다. 수정 모드를 붙일 때 버전 이동 영역의 조건을 '역할'이 아니라 '버전이 2개 이상인가'로 바꾼다.

**우선순위:** 중

---

## 5. 전체 거절 버튼이 없다

**충돌 대상:** REQ-038, FE-REFINE-008, BE-REFINE-008

**현재 동작**

`ContextPanel.tsx`의 정제 미리보기 하단에는 '전체 승인'과 '닫기'만 있다.

**무엇이 문제인가**

REQ-038이 전체 거절을 요구한다. 지금은 결과가 여러 개일 때 하나씩 거절하는 수밖에 없다.

**해결 방향**

'전체 승인' 옆에 '전체 거절'을 넣는다. 두 버튼 모두 대기 항목이 1개 이상일 때만 보이게 한다.

**우선순위:** 중

---

## 6. 거절한 정제 결과의 상태를 볼 수 없다

**충돌 대상:** REQ-032, FE-REFINE-002, FE-REFINE-006

**현재 동작**

`chatStore.ts`의 `refreshAfterDecision`은 승인이든 거절이든 처리한 항목을 결과 목록에서 지운다. 그래서 거절한 항목은 화면에서 곧바로 사라진다. 또 결과 항목에 상태 배지가 없다.

**무엇이 문제인가**

REQ-032는 각 정제 결과가 대기·승인됨·거절됨 중 하나를 표시해야 한다고 정한다. 지금은 어떤 상태도 표시되지 않고, 거절한 항목은 흔적 없이 사라져 사용자가 방금 무엇을 거절했는지 되짚을 수 없다.

REQ-038이 "전체 거절 버튼은 대기 항목이 없으면 숨긴다"고 따로 정한 것도, 거절된 항목이 목록에 남아 있는 상태를 전제한 문장이다.

**해결 방향**

승인한 항목만 목록에서 빼고, 거절한 항목은 '거절됨' 배지를 달아 남긴다. 대기 항목에는 '대기' 배지를 단다. 거절된 항목의 승인·거절 버튼은 지운다.

**우선순위:** 중

---

## 7. 전체 승인이 일부만 실패한 경우를 구분하지 않는다

**충돌 대상:** FE-NOTIFY-004, BE-NOTIFY-004, BE-REFINE-007

**현재 동작**

`chatStore.ts`의 `approveAll`은 요청이 성공하면 화면을 다시 불러오고 정제 작업을 통째로 비운다. 서버 응답의 성공·실패 구분을 읽지 않는다.

**무엇이 문제인가**

`BE-REFINE-007`은 성공 목록과 실패 목록을 나눠 돌려주고, `BE-NOTIFY-004`도 부분 실패를 별도 형식으로 정의한다. 지금 구조에서는 일부가 실패해도 전부 성공한 것처럼 정제 카드가 닫힌다. 사용자는 반영되지 않은 블록이 있다는 사실을 모른 채 넘어간다.

**해결 방향**

응답의 실패 목록을 읽어, 실패한 항목은 결과 목록에 남기고 오류 배너로 알린다.

**우선순위:** 중

---

## 8. 로그아웃 요청이 실패하면 화면이 그대로 남는다

**충돌 대상:** REQ-003, FE-AUTH-006

**현재 동작**

`api/auth.ts`의 `logout`은 토큰을 `finally`에서 지우지만 오류는 그대로 밖으로 던진다. `authStore.ts`의 `logout`은 이를 잡지 않아서, 서버 요청이 실패하면 `set({ user: null })`까지 가지 못한다.

**무엇이 문제인가**

토큰은 지워졌는데 화면은 로그인 상태로 남는다. 사용자는 로그아웃을 눌렀지만 아무 일도 일어나지 않은 것처럼 보이고, 이후 요청은 모두 인증 오류가 난다.

**해결 방향**

`authStore.logout`에서 오류를 잡고, 성공·실패와 무관하게 사용자 정보를 비운다.

**우선순위:** 중. 코드 몇 줄이지만 사용자가 빠져나갈 수 없는 상태가 된다.

---

## 9. 출발 Context가 없는 브랜치는 현재 브랜치 표시가 뜨지 않는다

**충돌 대상:** REQ-011, FE-BRANCH-003

**현재 동작**

`SourceContextBanner.tsx`는 출발 Context가 하나도 없으면 아무것도 그리지 않는다. 현재 브랜치 이름도 이 배너 안에 들어 있어 함께 사라진다.

**무엇이 문제인가**

Context 블록을 고르지 않고 브랜치를 만들면, 하위 브랜치에 있는데도 어느 브랜치인지 화면에 표시되지 않는다. 사이드바의 활성 표시로만 알 수 있다.

**해결 방향**

현재 브랜치 표시와 출발 Context 요약을 분리한다. 하위 브랜치면 이름은 항상 보이고, 출발 Context는 있을 때만 그 아래에 붙인다.

**우선순위:** 하

## 명세를 코드에 맞춰 고친 항목

아래 둘은 코드 쪽이 더 낫다고 보고 FE 기능명세서를 고쳤다. 요구사항이 금지하는 동작이 아니고, 코드에 그렇게 한 이유가 주석으로 남아 있다.

- **브랜치 생성 후 자동 전환** (FE-BRANCH-007) — 처음에는 사용자가 목록에서 골라 들어가는 것으로 적었으나, 코드는 만든 브랜치로 바로 들어간다. 목록만 갱신하면 방금 만든 브랜치가 어디 있는지 찾아야 한다는 이유가 타당해 명세를 코드에 맞췄다.
- **전송 후 적용 Context 자동 해제** (FE-CTXAPPLY-005) — 한 번 쓴 Context를 남겨두면 다음 질문까지 같은 맥락에 묶인다는 이유가 타당해 명세를 코드에 맞췄다. 요구사항에는 해제 시점이 정해져 있지 않다.

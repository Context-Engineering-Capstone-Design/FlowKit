## 2.13 다중 창 실시간 동기화

### BE-REALTIME-001 · 사용자별 실시간 이벤트 채널 구독

같은 계정으로 연결된 모든 창이 붙을 수 있는, 사용자 단위의 실시간 이벤트 통로를 연다.

**도메인**
User

**관련 요구사항**
REQ-073, REQ-074

**관련 화면**
없음 (화면에 표시되지 않는 내부 연결)

**입력**
userId

**처리**
그 사용자의 구독자 목록에 새 통로를 등록하고 연결을 열어 둔다. 데이터를 직접 담지 않고, 뭔가 바뀌었으니 "다시 확인해봐"라는 무효화 신호만 흘려보낸다 — 실제 상태는 항상 DB를 다시 조회해서 얻으므로 신호와 실제 상태가 어긋날 일이 없다. 연결이 오래 비어 있으면 하트비트를 보내 중간 경로가 idle 연결을 끊지 않게 한다. 연결이 끊기면 그 창의 구독을 목록에서 뺀다.

**출력**
연결 유지 중에는 발행되는 대화 목록 변화·답변 생성 활동 신호, 그 외에는 하트비트

**DB 영향**
없음

**상태 변화**
없음

**권한**
로그인 필요

**오류**
없음 (인증 실패는 로그인 공통 처리를 따른다)

**우선순위**
중

**비고**
BE-AIRESP-007의 답변 생성 스트리밍 통로(락으로 보호된 registry, 구독자별 큐, 하트비트)와 같은 구조를 쓰되, 키를 작업 하나가 아니라 사용자 하나로 바꿨다. 지금은 서버 프로세스 하나짜리 메모리 registry라 서버가 재시작되면 모든 연결이 끊긴다 — 여러 서버로 늘어나는 경우는 이번 범위 밖이다.

### BE-REALTIME-002 · 대화 목록 변화 발행

대화를 새로 만들거나, 지우거나, 제목이 바뀌면 그 사용자의 모든 구독 창에 목록을 다시 확인하라는 신호를 보낸다.

**도메인**
Chat

**관련 요구사항**
REQ-073

**관련 화면**
없음 (사이드바 갱신을 위한 내부 신호)

**입력**
userId (대화 생성·삭제·제목 변경이 일어난 시점의 소유자)

**처리**
새 대화 생성(메인·사이드 채팅·분기 노드 포함), 대화 삭제, 제목 변경이 끝날 때마다 BE-REALTIME-001의 통로로 그 사용자의 모든 구독 창에 목록 변화 신호를 보낸다. 신호에는 무엇이 바뀌었는지 담지 않는다 — 받은 창은 BE-CHAT-003(최근 대화 목록 조회)을 다시 호출해 최신 목록을 얻는다.

**출력**
통로로: 대화 목록 변화 신호

**DB 영향**
없음 (해당 변화 자체의 DB 반영은 각 기능이 이미 처리)

**상태 변화**
없음

**권한**
로그인 필요, 채팅 소유자

**오류**
없음

**우선순위**
중

**비고**
자기 자신이 방금 만든 변화의 신호도 그대로 받는다 — 화면 쪽에서 중복 반영을 막는 판단은 FE 책임(FE-REALTIME-002).

### BE-REALTIME-003 · 답변 생성 시작·완료 발행

답변 생성이 시작되거나 끝나면, 그 대화를 보고 있을 수 있는 다른 창에 다시 확인해보라는 신호를 보낸다.

**도메인**
AIResponse, Chat

**관련 요구사항**
REQ-074

**관련 화면**
없음 (열려 있는 대화 갱신을 위한 내부 신호)

**입력**
userId, chatId, branchId, aiResponseJobId(생성 시작 신호에만 포함)

**처리**
BE-AIRESP-007의 답변 생성 작업이 막 시작되면, 작업 id를 포함한 신호를 보낸다 — 같은 대화를 보고 있는 다른 창은 이 id로 BE-AIRESP-007의 스트리밍 통로에 붙을 수 있다. 생성이 끝나(완료·실패·중단) 최종 본문이 DB에 저장되면, 이번에는 작업 id 없이 신호를 보낸다 — 받은 창은 그 대화·브랜치를 다시 조회해 최종 상태를 반영한다. 생성 완료 신호는 사이드바의 생성 중·완료 배지도 바뀌므로 BE-REALTIME-002의 목록 변화 신호와 함께 보낸다.

**출력**
통로로: 답변 활동 신호(chatId, branchId, 시작이면 aiResponseJobId 포함)

**DB 영향**
없음 (해당 작업 자체의 DB 반영은 BE-AIRESP-007이 이미 처리)

**상태 변화**
없음

**권한**
로그인 필요, 채팅 소유자

**오류**
없음

**우선순위**
중

**비고**
사용자 메시지 전송(BE-AIRESP-001)뿐 아니라 재생성(BE-AIRESP-003)·실패 재시도도 같은 절차를 거치므로 셋 다 이 신호를 발행한다. 메시지 블록 생성 자체(BE-MSG-001)는 이 경로를 항상 거쳐 오므로 별도로 신호를 더 발행하지 않는다.

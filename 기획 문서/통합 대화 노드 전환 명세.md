# 통합 대화 노드 전환 명세

## 목적

브랜치와 사이드 채팅을 하나의 대화 노드 트리로 통합한다. 사용자는 어느 노드에서든 대화를 갈라 새 흐름을 만들 수 있으며, 화면과 데이터 모델은 브랜치·사이드 채팅을 별도 개념으로 다루지 않는다.

## 용어

| 용어 | 의미 |
| --- | --- |
| 루트 노드 | 사용자가 처음 만든 메인 대화 |
| 대화 노드 | 루트·일반·Temporary를 포함하는 하나의 대화 흐름 |
| 분기 노드 | 특정 노드의 메시지 시점에서 새로 만든 대화 노드 |
| 출발 흐름 | 분기 노드가 생성 때 참고하는 원본 노드의 확정된 메시지·Context 스냅샷 |

## 노드 구조

```text
메인
└─ 사이드 A
   ├─ 사이드 B
   └─ 분기 1
```

- 모든 노드는 하나의 `parent_chat_id`를 가진다. 루트 노드만 부모가 없다.
- 노드에서 분기하면 새 노드는 현재 노드의 자식이 아니라 현재 노드의 부모 아래에 생성한다.
- 따라서 `메인 → A → B`에서 B를 분기하면 새 노드는 A의 자식이며 B의 이웃이다.
- 메인에서 분기하면 메인이 새 노드의 부모다.
- 노드 이름은 분기 시 `분기 N`으로 자동 생성하고, 이후 이름을 바꿀 수 있다.

## 흐름과 Context 규칙

- 분기 노드는 생성 시점까지의 원본 메시지와 적용 Context를 스냅샷으로 고정한다.
- 원본 노드에 이후 메시지가 추가되거나 메시지 버전이 바뀌어도 분기 노드의 출발 흐름은 변하지 않는다.
- 이후 새 메시지는 생성된 노드에만 저장한다.
- 사용자가 드래그로 선택한 범위 Context는 현재 노드의 다음 요청에만 적용하며, 전송 뒤 비운다.

## Temporary 규칙

- 모든 깊이의 노드에서 일반 또는 Temporary를 선택할 수 있다.
- Temporary 노드는 기존 만료·탭 종료 정리 규칙을 유지한다.
- 일반 노드와 Temporary 노드는 같은 트리에서 표시하되, Temporary 상태와 보존 제한을 명확히 표시한다.

## 삭제 규칙

- 노드 삭제는 해당 노드와 하위 노드를 함께 삭제하는 명시적 전체 삭제만 제공한다.
- 하위 노드를 자동으로 승격하거나 부모를 바꾸지 않는다.
- 삭제 전 영향받는 노드·메시지·첨부 수를 보여주고 되돌릴 수 없음을 확인받는다.

## 기존 Branch 데이터 전환

1. 전환 전 데이터베이스 백업과 참조 수 검사를 수행한다.
2. 기존 Main Branch는 해당 Chat의 루트 노드 흐름으로 연결한다.
3. Child Branch는 새 대화 노드로 만든다. 기존 `parent_branch_id`와 `base_message_block_id`는 새 노드의 부모와 출발 시점으로 변환한다.
4. 메시지 블록, AI 작업, 정제 작업, Context 로그, 출발 Context, 첨부·평가·관측 기록의 `branch_id` 참조를 새 노드 흐름으로 옮긴다.
5. 이전·이후의 행 수, 사용자 소유권, 메시지 순서, 활성 버전, 출발 스냅샷을 비교한다.
6. 기존 `branchId` 조회와 링크는 한 릴리스 동안 읽기 호환을 제공한다.
7. 기존 Branch 테이블과 백업은 한 릴리스 동안 보관한 뒤, 검증 완료 후 제거한다.

## 전환 방식

- 구·신 구조를 병행하지 않는다.
- 점검 시간에 일괄 마이그레이션한다.
- 스테이징 환경에서 백업 복원, 전환, 회귀 검증, 롤백을 먼저 완료한다.
- 운영 전환 실패 시 백업으로 되돌린다.

## 후속 문서 갱신 순서

1. 요구사항정의서 `2.3 브랜치 관리`와 `2.2 채팅 관리`
2. FE 기능명세서 `2.2 채팅 관리`, `2.3 브랜치 관리`
3. BE 기능명세서 `2.2 채팅 관리`, `2.3 브랜치 관리`, AI 응답·정제·Context 참조 문서
4. AI 기능명세서의 입력 스냅샷·출발 흐름 설명

이 문서가 위 후속 문서 갱신 전까지 통합 대화 노드의 우선 설계 기준이다.

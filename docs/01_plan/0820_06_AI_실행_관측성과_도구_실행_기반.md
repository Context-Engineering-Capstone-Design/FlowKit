# 0820_06 AI 실행 관측성과 도구 실행 기반

- 상태: 계획

## 배경

FlowKit은 답변 생성 작업, 스트리밍, 중단, Context, 첨부 파일, 검색 근거를 이미 각 기능으로 갖추고 있다. 그러나 한 요청이 실제로 어떤 경로를 거쳤는지 한곳에서 볼 수 없다.

- 첫 글자가 언제 왔는지, 전체 생성이 얼마나 걸렸는지 알 수 없다.
- 선택한 모델·추론 단계·검색 모드와 실제 결과를 한 작업 단위로 비교하기 어렵다.
- Context·첨부·검색 근거가 답변에 어떤 방식으로 쓰였는지 공통 형식으로 남지 않는다.
- 이후 빠른 답변·깊은 조사·자동 라우팅을 평가할 근거가 없다.

ChatGPT식 조사·도구 사용 경험을 만들기 전에, 실행 경로를 안전하게 기록하고 검증할 기반부터 만든다. 이 마일스톤은 새 조사 화면이나 자동 라우터를 만들지 않는다.

## 목표

1. AI 답변 작업마다 서버 생성 시간과 화면 전달 시간을 측정한다.
2. Context, 첨부, 웹 검색처럼 답변 근거에 영향을 준 입력·도구를 같은 실행 기록으로 남긴다.
3. 실제로 확인하지 못한 도구 실행을 화면이나 기록에서 성공으로 꾸미지 않는다.
4. 다음 조사 모드와 라우터가 품질·지연 시간·비용을 비교할 수 있는 최소 데이터를 만든다.

## 기획 명세 상태

AI 실행 관측성, 도구 실행 기록, 조사 모드는 현재 `기획 문서/`에 기능으로 정의돼 있지 않다. 구현 착수 전 아래 항목을 요구사항·AI·BE·FE 기능명세에 추가하는 승인이 필요하다.

- AI 실행 시간과 근거 사용 기록
- 사용자에게 보여 줄 실행 상태와 근거 정보 범위
- 실행 기록의 보관 기간과 열람 권한

이 문서는 구현 계획일 뿐, 위 기획 문서를 변경하지 않는다.

## 범위

### 포함

- 답변·재생성·실패 재시도 작업의 실행 시간 기록
- Context·첨부·웹 검색의 실행 기록 계약
- 민감정보를 저장하지 않는 관측 데이터 모델과 조회 API
- 프론트엔드 전달 시간 측정과 오류·중단 구분
- 고정 시나리오 기반의 지연 시간·근거 기록 검증

| 항목 | 제외 이유 |

| 자동 라우터·작은 모델 분류기 | 기록과 평가 데이터가 없는 상태에서 자동 경로를 바꾸지 않는다. |

| 코드 실행 환경, 외부 앱·MCP, 장기 메모리 | 도구 권한·비용·보안 정책이 별도로 필요한 큰 범위다. |
| 원문 질문·첨부 본문·API 키·접근 토큰의 관측 저장 | 개인정보·비밀값 노출 위험이 있어 저장하지 않는다. |

## 확정할 설계 원칙

| 항목 | 제안 | 이유 |
| --- | --- | --- |
| 실행 단위 | 기존 `AiResponseJob` 하나를 실행의 기준으로 쓴다 | 생성·재생성·재시도 상태와 연결할 수 있다 |
| 시간 측정 | 서버 생성 시작·첫 조각·완료·중단과 화면 수신·첫 표시 시각을 분리한다 | 모델 지연, 서버 중계 지연, 화면 렌더링 지연을 구분한다 |
| 근거 기록 | Context·첨부·검색을 같은 실행 이벤트 형식으로 기록한다 | 이후 도구가 늘어도 조회·평가 방식이 흩어지지 않는다 |
| 검색 실제 실행 | 공급자 이벤트 또는 검색 근거로 확인된 경우만 `completed`로 기록한다 | `auto`가 검색 도구를 받았다는 사실과 실제 검색은 다르다 |
| 개인정보 | 식별자·개수·크기·시간·상태만 저장하고 원문은 저장하지 않는다 | 관측 기능이 새 데이터 유출 경로가 되는 것을 막는다 |
| 사용자 노출 | 이번에는 개발·운영용 조회만 만든다 | 정확하지 않은 ‘검색 중’·‘분석 중’ 화면을 먼저 만들지 않는다 |

## 마일스톤 A · 실행 시간 기록

답변 생성 시작부터 끝까지의 서버 시간을 `AiResponseJob`에 연결해 기록한다.

- [ ] A1. 생성 시작, 첫 모델 조각 수신, 완료, 실패, 중단 시각을 정의한다.
- [ ] A2. 생성·재생성·재시도의 모든 경로에서 같은 시각을 기록한다.
- [ ] A3. 서버 재시작으로 멈춘 작업은 완료 시간이 아니라 실패 정리 시각과 사유를 남긴다.
- [ ] A4. 첫 조각이 없는 실패·빈 응답·중단을 구분한다.
- [ ] A5. 기존 작업 스냅샷과 호환되는 DB 마이그레이션·조회 코드를 작성한다.

**완료 기준**: 완료·실패·중단·서버 재시작 정리 작업 각각에서 생성 시간, 첫 조각까지 걸린 시간, 최종 상태를 구분해 조회할 수 있다.

---

## 마일스톤 B · 도구·근거 실행 기록 계약

답변에 영향을 준 입력과 도구 실행을 공통 이벤트로 남긴다. 이 이벤트는 답변 본문을 저장하는 기능이 아니다.

- [ ] B1. 실행 이벤트에 `kind`, `status`, `startedAt`, `completedAt`, 안전한 요약 정보를 둔다.
- [ ] B2. 현재 대상 `context_read`, `attachment_read`, `web_search`를 정의한다.
- [ ] B3. Context는 선택 블록 수·버전 식별자만, 첨부는 파일 식별자·형식·크기만 기록한다.
- [ ] B4. 웹 검색은 요청 모드, 검색 근거 수, 공급자가 실제 실행을 알려 주는지 여부를 분리해 기록한다.
- [ ] B5. 검색 근거가 없고 공급자 실행 이벤트도 없으면 `unknown`으로 남긴다. `completed`로 추정하지 않는다.
- [ ] B6. 이벤트 조회 응답에는 API 키, 질문 원문, 첨부 본문, 검색 질의 원문을 넣지 않는다.

**완료 기준**: 한 AI 작업의 Context·첨부·검색 관련 기록을 시간순으로 조회할 수 있고, 검색 모드와 실제 검색 확인 상태가 혼동되지 않는다.

## 마일스톤 C · 화면 전달 시간과 안전한 조회

서버가 조각을 만들었어도 화면이 늦게 보이면 사용자는 응답이 느리다고 느낀다. 브라우저에서 측정 가능한 지표를 서버 실행 기록과 연결한다.

- [ ] C1. 전송 클릭, 응답 블록 표시, 스트림 연결, 첫 조각 화면 반영, 완료·중단·연결 실패를 기록한다.
- [ ] C2. 화면 시간은 기존 작업 ID와 연결하되, 질문·답변 본문을 관측 API로 보내지 않는다.
- [ ] C3. 연결 재시도는 별도 횟수와 최종 결과로 남긴다.
- [ ] C4. 작업 소유자만 자신의 실행 요약을 조회하게 한다.
- [ ] C5. 개발·운영 조회 API는 화면의 일반 대화 흐름과 분리하고, 서비스 오류 수집 API와 목적을 섞지 않는다.

**완료 기준**: 같은 작업에서 서버 첫 조각 시각과 화면 첫 표시 시각을 비교할 수 있으며, 재접속 실패와 모델 생성 실패를 구분할 수 있다.

## 마일스톤 D · 평가 기준과 최소 보고서

라우터나 조사 모드를 만들기 전에, 현재 경로가 실제로 적절한지 확인할 수 있는 평가 기준을 고정한다.

- [ ] D1. 고정 시나리오를 만든다: 짧은 대화, 긴 설명, Context 적용, 첨부 사용, 검색 미사용, 검색 사용, 중단, 재접속.
- [ ] D2. 시나리오마다 첫 글자까지 시간, 완료 시간, 실행 이벤트, 오류·중단 상태를 확인한다.
- [ ] D3. 추론 단계·모델·검색 모드별 결과를 비교할 수 있는 내부용 요약을 만든다.
- [ ] D4. 비용은 공급자 응답에서 신뢰할 수 있는 사용량이 제공될 때만 기록한다. 없으면 ‘미측정’으로 남긴다.
- [ ] D5. 라우터 도입 판단 기준을 문서화한다: 검색 누락률, 불필요 검색률, 지연 시간, 재시도율, 사용자 평가.

**완료 기준**: 새 경로를 추가하기 전과 후에 같은 시나리오의 품질·지연 시간·도구 사용을 비교할 수 있다.

## 마일스톤 E · 다음 조사 모드의 경계 확정

조사 모드는 이번에 구현하지 않는다. 대신 다음 계획이 추측으로 시작하지 않도록 입·출력 경계를 정리한다.

- [ ] E1. 조사 모드가 사용할 수 있는 근거 범위(웹, 첨부, Context)를 확정한다.
- [ ] E2. 조사 계획을 사용자에게 보여 주고 수정·중단하게 할지 결정한다.
- [ ] E3. 근거별 인용 규칙과 최종 보고서 형식을 정한다.
- [ ] E4. 장시간 실행의 작업 보관·재개·실패 처리 기준을 정한다.
- [ ] E5. 단일 서버의 프로세스 메모리 중계 구조를 유지할지, 여러 서버를 위한 공유 작업 큐를 도입할지 배포 목표에 따라 결정한다.

**완료 기준**: 다음 조사 모드 계획이 사용할 도구, 사용자 통제, 작업 지속성, 인용 방식이 문서상 확정돼 있다.

## 검증 방법

- 백엔드 자동 테스트: 실행 시간 기록, 상태 전이, 소유권, 민감정보 비저장, 검색 `unknown` 처리를 확인한다.
- 프론트엔드 자동 테스트: 첫 표시·재접속·중단·전달 실패 측정값 전송을 확인한다.
- 통합 테스트: 가짜 모델과 실제 스트림으로 서버·화면 시간의 순서가 맞는지 확인한다.
- 로컬 브라우저 직접 확인: 짧은 답변, 긴 답변, 중단, 재접속에서 체감 상태와 기록이 일치하는지 확인한다.
- 회귀 테스트: 기존 스트리밍, Context, 첨부, 검색 근거, 재생성·재시도 흐름이 유지되는지 확인한다.

## 구현 전 결정이 필요한 항목

1. 실행 기록 보관 기간과 사용자 삭제 시 처리 방식
2. 개발·운영용 실행 요약을 사용자 화면에도 공개할지 여부
3. 실제 비용 측정이 가능한 공급자 사용량 정보를 어디까지 저장할지
4. 단일 서버를 전제로 할지, 조사 모드 전에 공유 작업 큐를 도입할지

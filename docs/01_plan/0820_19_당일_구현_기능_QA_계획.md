# 0820_19 8월 20일 구현 기능 QA 계획

## 목표

오늘(2026-08-20) "구현 완료"로 기록된 16개 마일스톤을 실제 Chrome 브라우저로 클릭하며 확인한다. 각 결과 문서에는 자동 테스트(백엔드 pytest, 프론트 vitest, 빌드)는 대부분 통과했지만, 실제 화면에서 클릭해 확인하지 못했다고 적힌 항목이 많다. 이번 QA는 그 미확인 항목을 실제 화면에서 눈으로 보고 검증하는 것이 목적이다. 시간을 넉넉히 쓸 수 있으므로, 문제를 발견하면 기록만 하지 않고 그 자리에서 원인을 찾아 수정하고 재검증까지 마친다.

## 배경

- 오늘 커밋 85건, 결과 문서 17건(`0820_01`~`0820_17`)이 작성됐다.
- 문서별로 검증 상태가 다르다. [`0820_08`](../02_result/0820_08_사이드_채팅_트리와_선택적_메인_반영.md)은 로컬 개발 로그인과 실제 OpenAI 키로 브라우저 수동 확인을 이미 마쳤다. 나머지 대부분은 자동 테스트만 통과했고, [`0820_11`](../02_result/0820_11_Projects.md)과 [`0820_12`](../02_result/0820_12_사이드바_생성_상태와_완료_도트.md)는 검증 체크리스트 자체가 대부분 비어 있다.
- **(갱신, 2026-08-21)** [`0820_18`](0820_18_브랜치와_사이드_채팅_대화_노드_통합.md) 계획이 [`0820_20_통합_대화_노드_구현과_전환`](../02_result/0820_20_통합_대화_노드_구현과_전환.md)으로 구현·전환까지 완료됐다(기준 커밋 `e03adc7`, 후속 `ab32977`). 기존 Branch는 통합 Chat 노드로 전환됐고, 좌측 "대화 구조"는 Branch 목록 없이 노드 트리만 표시한다. 이 문서도 브라우저 수동 검증은 하지 않았다고 명시돼 있어 QA 대상에 새로 포함한다. [03]·[08]·[10]·[16]·[17]은 이 전환 이후의 화면(브랜치와 사이드 채팅이 하나의 노드 트리로 통합된 상태) 기준으로 확인한다 — 옛 문서의 "브랜치/사이드 채팅 구분" 표현은 지금 화면과 다를 수 있으니 실제 동작(형제 위치 생성, 부모 맥락 참고, Temporary 규칙)이 유지되는지를 기준으로 판단한다.

## 범위

- 포함: 아래 마일스톤별 검증 방법에 나열한 17개 구현 마일스톤(`0820_02`~`0820_17`, `0820_20`)의 사용자 화면 동작. `0820_01`은 구현 문서가 아니라 조사 문서라 QA 대상이 아니고, 참고용으로만 다룬다.
- 제외: `0820_06` AI 실행 관측성(일반 사용자 화면에 노출되지 않는 개발용 API라 우선순위 최하로만 참고 확인).
- 실행 환경: 로컬 백엔드(8000번 포트)·프론트(5173번 포트), Chrome 브라우저로 원격 접속. 로그인은 `DEV_LOGIN_ENABLED` 로컬 개발 로그인을 사용한다([`0819_01`](../03_others/0819_01_FlowKit_로컬_서버_실행_안내.md) 참고). 답변 생성이 포함된 시나리오는 사용자 계정에 등록된 OpenAI API 키가 필요하다.

## 사전 준비

QA를 몇 시간에 걸쳐 진행할 예정이므로, 시작 전에 아래를 먼저 갖춰두면 중간에 끊기지 않는다.

### 서버·계정 준비

- [ ] PostgreSQL 실행 확인 (`brew services list` 또는 `docker compose ps`)
- [ ] 백엔드 실행: `cd backend && source .venv/bin/activate && alembic upgrade head && uvicorn app.main:app --reload --port 8000`, `http://127.0.0.1:8000/health`에서 `{"status":"ok"}` 확인
- [ ] 프론트 실행: `cd frontend && npm run dev`, `http://localhost:5173` 접속 확인
- [ ] `backend/.env`의 `DEV_LOGIN_ENABLED=true`, `frontend/.env`의 `VITE_DEV_LOGIN_ENABLED=true` 확인 (Chrome 원격 접속 로그인용, [`0819_01`](../03_others/0819_01_FlowKit_로컬_서버_실행_안내.md) 참고)
- [ ] 로그인 후 설정 화면에서 OpenAI API 키가 등록돼 있는지 확인. 없으면 먼저 등록한다(답변 생성이 필요한 시나리오 대부분이 이 키에 의존한다)
- [ ] [06]의 "다른 사용자 계정으로 조회 시 거부" 확인용으로, 두 번째 계정(또는 두 번째 로컬 로그인 세션)을 하나 더 준비해둔다

- [ ] **긴 대화 하나** ([07] 목차 레일 확인용): 스크롤이 충분히 생기도록 질문·답변을 10턴 이상 주고받은 대화
- [ ] **브랜치가 있는 대화** ([03], [08], [17] 확인용): 답변 하나를 분기점으로 브랜치를 미리 하나 만들어둔다

## 문제 발견 시 처리 원칙

- **해당 마일스톤 결과 문서(`docs/02_result/0820_NN_...`)에 이미 적힌 목표·완료 기준 범위 안의 문제**는 발견 즉시 원인을 찾아 고치고, 같은 화면에서 재검증한다. 예: "형제 브랜치 생성이 오류를 낸다"([03]의 완료 기준에 이미 있는 항목)는 바로 수정한다.
- **기획 문서(`기획 문서/`)나 결과 문서 어디에도 없는 동작을 요구하는 문제**도 사용자가 앞으로 몇 시간 동안은 판단을 기다리지 말고 임의 판단하라고 승인했으므로, 답을 기다리지 않고 바로 판단해 고친다. 다만 어떤 명세 밖 판단을 내렸는지는 "발견된 문제" 절에 반드시 남긴다.
- 이 자율 판단 승인에도 다음은 예외로 두고, 발생하면 진행을 멈추고 사용자에게 알린다: 원격 저장소로 `push`/`force-push`, 기존 데이터·문서의 영구 삭제, DB 마이그레이션처럼 되돌리기 어려운 구조 변경, `기획 문서/` 자체의 직접 수정(스펙 반영은 QA 종료 후 별도로 확인).
- 이렇게 명세 밖에서 새로 정한 동작은 QA가 끝난 뒤 관련 `기획 문서/`에 반영할지 사용자와 별도로 확인한다(이 문서만으로 기획 문서를 임의로 고치지 않는다).
- 수정 하나마다 관련 없는 다른 변경과 섞지 않고 그 문제 하나만 다루는 커밋으로 분리한다(수정 파일이 소규모면 한 커밋, 여러 마일스톤에 걸치면 마일스톤별로 나눈다).
- 수정 후에는 그 마일스톤의 자동 테스트(백엔드 `pytest`/프론트 `pnpm test`, 필요시 `pnpm build`)를 다시 돌려 회귀가 없는지 확인한다.
- 수정이 끝나면 **해당 결과 문서**(`docs/02_result/0820_NN_...`)의 완료 기준 체크박스·검증 결과·남은 제한 사항도 함께 갱신한다. 기존 "구현 결과" 절은 지우지 않고, `0820_10` 문서의 "컨텍스트 규칙 보완" 사례처럼 QA에서 발견해 고친 내용을 새 항목으로 덧붙인다.
- 이렇게 결과 문서를 고친 커밋은 코드 수정 커밋과 분리해 "docs:" 커밋으로 별도로 만든다.

- [ ] **Project + 드래그 Context**: Project 소속 대화에서 드래그로 텍스트를 선택해 "채팅에 추가"·"사이드 채팅에 질문"이 정상 동작한다

- [ ] **긴 대화 + 스트리밍 + 목차**: 답변이 스트리밍 중인 상태에서 목차 레일([07])의 항목을 눌러 이동해도 스트리밍이 끊기지 않는다
- [ ] **Temporary + 드래그 Context**: Temporary 사이드 채팅에서는 드래그해도 "채팅에 추가"만 되고 부모 반영 관련 옵션은 제한된다([10]의 제한 규칙과 [13]의 드래그 기능이 함께 지켜지는지)

### [02] OpenAI 연결 실패로 답변 생성 전체가 막힘

### 참고 — 자동화 환경 제약: 네이티브 `confirm()` 대화상자

Project 삭제 버튼은 브라우저 기본 `confirm()`을 쓴다. 이 QA에 쓰는 Chrome 자동화 도구에서는 `confirm()`이 자동으로 취소(false) 처리돼, 실제 사용자 클릭과 달리 버튼을 눌러도 삭제가 진행되지 않았다. `window.confirm`을 임시로 `true`를 반환하도록 바꾼 뒤에야 삭제 흐름을 검증할 수 있었다. 이후 네이티브 confirm/alert을 쓰는 다른 삭제 버튼(대화 삭제 등)도 이 도구로 자동 클릭 검증할 때 같은 우회가 필요할 수 있다. 이 자체는 이미 [`0820_01`](../02_result/0820_01_기능명세_추가_대조_조사.md)의 하 우선순위 항목(네이티브 확인창 사용)으로 알려진 내용이라 별도 수정은 하지 않는다.

# 배포 환경변수 체크리스트

Vercel(프론트엔드)·Render(백엔드)·Neon(PostgreSQL)·Upstash(Redis)로 배포할 때, 각 플랫폼 대시보드에 직접 채워야 하는 값을 정리했다. 개발용과 운영용을 완전히 분리된 값(서로 다른 DB, 서로 다른 비밀키)으로 채워야 한다 — 같은 값을 공유하면 개발 중 실험이 운영 데이터에 영향을 줄 수 있다.

## 순서

1. Neon에서 PostgreSQL 프로젝트를 개발용·운영용 2개(또는 브랜치 2개) 만들고 접속 주소를 각각 받는다.
2. Upstash에서 Redis 데이터베이스를 개발용·운영용 2개 만들고 접속 주소를 각각 받는다.
3. Render에서 [render.yaml](../../render.yaml)에 정의된 `flowkit-backend-dev`, `flowkit-backend-prod` 두 웹 서비스를 Blueprint로 만들고, 아래 표의 값을 각 서비스에 채운다.
4. Vercel에서 프로젝트를 만들 때 저장소 하위 폴더를 프론트엔드 폴더로 지정하고, 아래 프론트엔드 값을 채운다.

## 백엔드 (Render)

| 값 | 어디서 구하는가 | 비고 |
|---|---|---|
| `DATABASE_URL` | Neon 프로젝트의 접속 문자열 | `postgresql+psycopg://...` 형식으로 앞부분을 맞춰야 한다 |
| `REDIS_URL` | Upstash 데이터베이스의 접속 문자열 | |
| `JWT_SECRET` | 직접 생성 | `python -c "import secrets; print(secrets.token_urlsafe(48))"`. 개발·운영 각각 새로 생성 |
| `API_KEY_ENCRYPTION_KEY` | 직접 생성 | `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. 개발·운영 각각 새로 생성 |
| `GOOGLE_CLIENT_ID` | Google Cloud Console의 OAuth 클라이언트 | 개발·운영 프론트엔드 주소를 승인된 리디렉션에 각각 등록해야 한다 |
| `CORS_ORIGINS` | 프론트엔드 배포 주소 | JSON 배열 형식이어야 한다. 예: `["https://flowkit.vercel.app"]` |
| `DEV_LOGIN_ENABLED` | 항상 `false` | 운영 전용 로그인 우회 기능을 배포 환경에서 켜지 않는다 |

## 프론트엔드 (Vercel)

| 값 | 내용 | 비고 |
|---|---|---|
| `VITE_API_BASE_URL` | 대응하는 백엔드 주소 | dev 배포는 `flowkit-backend-dev`, 운영 배포는 `flowkit-backend-prod` 주소 |
| `VITE_GOOGLE_CLIENT_ID` | 백엔드와 같은 Google OAuth 클라이언트 ID | |
| `VITE_DEV_LOGIN_ENABLED` | 항상 `false` | |

## 알려진 제한사항

- 첨부 파일은 현재 백엔드 서버의 로컬 디스크에 저장된다. Render 기본 웹 서비스는 재배포 시 디스크가 초기화될 수 있어, 재배포할 때마다 이미 올라간 첨부 파일이 사라질 수 있다. 지금은 이 상태로 배포하고, 필요해지면 외부 저장소(S3 호환 등)로 옮기는 작업을 별도로 진행한다.
- `render.yaml`의 `flowkit-backend-dev` 서비스는 저장소에 `dev` 브랜치가 있어야 배포된다. 아직 `dev` 브랜치가 없다면 먼저 만들어서 원격에 올려야 한다.

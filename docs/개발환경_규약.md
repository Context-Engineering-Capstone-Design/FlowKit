# 개발환경 규약

팀원 4명이 각자 다른 환경에서 작업하다 나중에 합칠 때 깨지지 않도록, 어떤 도구를 어떤 버전으로 쓸지 정해둔 문서다. 새로 합류하거나 새 노트북에서 시작할 때 이 문서만 따라 하면 되게 하는 것이 목표다.

## 한눈에 보기

| 영역 | 사용 기술 | 위치 |
| --- | --- | --- |
| 프론트엔드 | React + TypeScript + Vite, Tailwind CSS | `frontend/` |
| 백엔드 | FastAPI + PostgreSQL (SQLAlchemy) | `backend/` |
| AI 모델링 | LangChain / LangGraph + Gemini | `modeling/` |

**중요한 구조 결정 두 가지**

- `modeling/`은 따로 서버를 띄우지 않는다. 실행할 때는 백엔드가 파이썬 패키지로 직접 가져다 쓴다. 다만 **개발용 가상환경은 백엔드와 따로 둔다** — AI 담당자가 백엔드 없이도 프롬프트와 체인을 단독으로 돌려보고 테스트할 수 있어야 하기 때문이다.
- 프론트엔드만 별도 프로세스로 뜬다. 백엔드와는 HTTP로만 통신한다.

## 버전 고정

아래 버전을 기준으로 맞춘다. 다르면 같은 코드가 사람마다 다르게 동작할 수 있다.

| 항목 | 버전 |
| --- | --- |
| Node.js | 26.x |
| npm | 11.x (Node에 포함, 별도 설치 불필요) |
| Python | 3.14.x |
| PostgreSQL | 16.x |

프론트엔드 주요 패키지는 설치 후 동작을 확인한 버전이다. React 19, Vite 8, TypeScript 6, Tailwind 4를 쓴다. 정확한 버전은 `frontend/package.json`과 `package-lock.json`에 있으니, 팀원은 `npm install`만 하면 같은 버전이 깔린다.

패키지 매니저는 **npm**을 쓴다. yarn이나 pnpm으로 설치하면 `package-lock.json`과 어긋나므로 섞어 쓰지 않는다.

## 프론트엔드 (`frontend/`)

### 기술 선택

| 용도 | 선택 | 이유 |
| --- | --- | --- |
| 빌드 도구 | Vite | 로그인 후 화면이 하나인 앱이라 서버 렌더링이 필요 없다. 설정이 가볍고 개발 서버가 빠르다. |
| 언어 | TypeScript | API 응답 구조가 복잡해서(블록·버전·브랜치) 타입이 없으면 실수가 잦다. |
| 스타일 | Tailwind CSS v4 | UI 시안이 이미 색·간격을 값으로 정의해 두어 그대로 옮기기 좋다. |
| 상태 관리 | Zustand | 선택된 블록, 적용 중인 Context처럼 화면 여러 곳이 함께 보는 상태가 있다. Redux는 이 규모에 과하다. |
| HTTP | axios | 토큰 만료 시 자동 재발급을 한 곳에서 처리하기 좋다. |
| 아이콘 | lucide-react | UI 시안이 이미 lucide 아이콘을 쓴다. |
| 마크다운 | react-markdown | AI 응답이 마크다운으로 온다. |

### 폴더 구조

```
frontend/src/
├── api/          백엔드 호출 (인증 토큰 처리 포함)
├── components/   화면 조각
├── store/        Zustand 상태
├── types/        백엔드 응답 타입
└── App.tsx
```

### 규칙

- 컴포넌트를 새로 만들면 `export function` 바로 위에 그 컴포넌트가 화면에서 맡는 역할을 한 줄 주석으로 적는다.
- 백엔드 주소는 코드에 직접 쓰지 않고 `.env`의 `VITE_API_BASE_URL`을 쓴다.
- API 응답 필드는 camelCase다(백엔드가 그렇게 내보낸다). 별도 변환 없이 그대로 쓴다.
- import 경로는 `@/` 별칭을 쓴다 (`@/api/client` → `src/api/client`).
- 색은 직접 쓰지 말고 `src/index.css`에 정의한 토큰을 쓴다. UI 시안의 값을 옮겨둔 것이라, 시안과 화면이 어긋나지 않는다.

### 토큰 재발급 주의

백엔드는 재발급할 때마다 refreshToken을 새로 바꾸고 기존 것을 폐기한다. 그래서 요청 여러 개가 동시에 토큰 만료를 만나 각자 재발급을 부르면, 두 번째부터는 이미 폐기된 토큰을 보내게 되고 서버는 이를 탈취로 보아 **모든 세션을 끊는다.**

`src/api/client.ts`가 재발급을 한 번에 하나만 진행하도록 묶어 두었다. 인증 관련 코드를 손볼 때 이 부분을 깨지 않도록 주의한다.

## 백엔드 + AI 모델링 (`backend/`, `modeling/`)

### 가상환경은 둘로 나누되, 실행은 백엔드 환경에서 한다

```
backend/.venv     백엔드 실행용. 백엔드 + 모델링 의존성을 모두 설치한다.
modeling/.venv    AI 담당자 단독 작업용. 모델링 의존성만 설치한다.
```

AI 담당자는 `modeling/.venv`에서 프롬프트와 체인을 바로 실행·테스트할 수 있다. 백엔드나 DB를 띄우지 않아도 된다.

`modeling`은 설치 가능한 패키지다. 백엔드는 아래처럼 설치하면 경로 설정 없이 `import modeling`이 되고 필요한 의존성도 함께 딸려온다.

```bash
cd backend && source .venv/bin/activate
pip install -e ../modeling
```

`-e`(편집 가능 설치)라서 modeling 코드를 고치면 백엔드에 바로 반영된다. 매번 다시 설치하지 않아도 된다.

**단, 의존성 목록을 바꿨을 때는 다시 설치해야 한다.** 환경이 둘로 나뉘어 있어, modeling 쪽에서만 패키지를 올리고 백엔드 환경에 반영하지 않으면 단독 테스트는 통과하는데 서버에서는 실패한다.

의존성은 `modeling/pyproject.toml`에 적는다. `requirements.txt`는 단독 작업용 사본이므로 두 파일을 함께 맞춘다.

### AI 모델링 기술 선택

LangChain / LangGraph로 시작한다. 지금 필요한 건 블록별 정제와 제목 생성 정도지만, 이후 Self-Correction 루프와 RAG를 붙일 계획이 최종보고서에 있어 처음부터 체인 구조를 잡아두는 편이 갈아엎는 비용보다 낫다.

LangChain은 버전 간 호환이 자주 깨지므로 상한을 걸어 두었다(LangChain 1.x, LangGraph 1.x). 올릴 때는 동작을 확인하고 팀에 공유한 뒤 고친다.

모델은 Gemini 2.5 Flash를 쓴다. 정제와 제목 생성은 무거운 모델이 필요 없는 작업이다.

### 폴더 구조

```
backend/app/
├── models/     DB 테이블 정의
├── schemas/    API 입출력 형식
├── services/   실제 로직
├── routers/    엔드포인트
└── core/       토큰 등 공통 기능

modeling/
├── prompts/    프롬프트 문안
└── chains/     LangChain 체인
```

### 규칙

- 로직은 `services/`에 두고 `routers/`는 얇게 유지한다. 테스트할 때 HTTP 없이 로직만 검증할 수 있다.
- 오류는 `app/exceptions.py`의 형식을 따른다. 프론트가 `errorCode`로 분기하므로 새 오류를 만들 때도 같은 형식을 쓴다.
- 비밀값은 `.env`에만 두고 절대 커밋하지 않는다. 새 항목을 추가하면 `.env.example`에 빈 값으로 같이 넣어 팀원이 무엇을 채워야 하는지 알 수 있게 한다.

## 처음 시작하기

### 1. 저장소

```bash
git clone https://github.com/Context-Engineering-Capstone-Design/FlowKit.git
cd FlowKit
```

### 2. PostgreSQL

```bash
brew install postgresql@16
brew services start postgresql@16
export PATH="/opt/homebrew/opt/postgresql@16/bin:$PATH"   # 셸 프로필에 추가

psql -d postgres -c "CREATE ROLE flowkit LOGIN PASSWORD 'flowkit';"
psql -d postgres -c "CREATE DATABASE flowkit OWNER flowkit;"
```

Docker를 이미 쓰고 있다면 `docker compose up -d`로 대신해도 된다. 둘 다 할 필요는 없다.

### 3. 백엔드 (서버를 띄우는 사람)

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -e ../modeling     # 서버가 modeling 을 import 한다
cp .env.example .env

alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

`http://127.0.0.1:8000/docs`에서 API 목록을 확인한다.

### 3-1. 모델링만 작업하는 경우

백엔드나 DB 없이 프롬프트·체인만 다룰 때 쓴다.

```bash
cd modeling
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
pytest tests/ -q
```

테스트는 실제 API를 부르지 않으므로 키 없이 돌아간다.

### 4. 프론트엔드

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

`http://localhost:5173`에서 열린다.

## 환경변수

값이 없으면 서버가 뜨지 않거나 기능이 막히므로, 각자 로컬에서 채워야 한다.

| 변수 | 위치 | 설명 |
| --- | --- | --- |
| `DATABASE_URL` | backend | PostgreSQL 접속 주소 |
| `REDIS_URL` | backend | 아직 사용 안 함. 나중에 세션 캐시로 쓸 예정 |
| `GOOGLE_CLIENT_ID` | backend | Google 로그인 검증용. 없으면 로그인이 막힌다 |
| `JWT_SECRET` | backend | 32자 이상. 짧으면 서버가 아예 뜨지 않는다 |
| `GOOGLE_API_KEY` | backend | AI 호출용. 사용자별 키 입력 기능은 나중에 |
| `VITE_API_BASE_URL` | frontend | 백엔드 주소 (`http://127.0.0.1:8000`) |

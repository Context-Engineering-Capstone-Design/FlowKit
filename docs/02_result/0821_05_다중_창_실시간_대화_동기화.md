# 0821_05 다중 창 실시간 대화 동기화

- 상태: 구현 완료
- 기준 커밋: `65763f3`
- 앞선 논의: 같은 세션 안의 방향 논의(A안 채택 — 기존 SSE 패턴을 사용자 단위로 일반화)

## 배경

같은 계정으로 브라우저 창(또는 탭)을 두 개 띄워 놓고 한쪽에서 대화를 이어가면, 다른 쪽 창은 그 변화를 전혀 모른다.

- **사이드바 최신 대화 목록**: [chatStore.ts:73](../../frontend/src/store/chatStore.ts)의 `syncChatStatusPolling`이 2.5초 폴링을 하지만, **자기 화면의 `chats` 목록에 이미 생성 중인 항목이 있어야만 폴링이 켜진다.** 창 B가 가만히 있으면 폴링 자체가 시작되지 않아 새 대화가 생겨도, 제목이 바뀌어도 모른다.
- **AI 답변 스트리밍**: [conversation.py](../../backend/app/routers/conversation.py)의 `/ai-response-jobs/{job_id}/stream`과 [streaming_service.py](../../backend/app/services/streaming_service.py)의 pub/sub은 잘 만들어져 있지만, **이미 `job_id`를 아는 화면만** 붙을 수 있다. 창 B는 창 A가 새 job을 시작했다는 사실 자체를 알 방법이 없다.
- **열려 있는 대화 내용**: [chatStore.ts:678](../../frontend/src/store/chatStore.ts)의 `openChat`은 클릭한 시점에 한 번만 불러온다. 그 뒤로 재조회하는 코드가 없다.

공통 원인은 하나다. **"내가 모르는 변화가 생겼다"를 알려주는 채널이 없다.** 있는 건 전부 "이미 아는 것을 이어보기"뿐이다.

반가운 사실도 있다. 사이드바의 생성 중·완료 배지(`isGenerating`, `hasUnseenCompletion`)는 [chat_service.py의 `list_chat_activity_states`](../../backend/app/services/chat_service.py)가 매번 DB(`AiResponseJob`, `ChatReadState`)를 다시 읽어 계산한다. 즉 **어느 창이 무엇을 시작했든 상태 자체는 이미 정확하다.** 부족한 건 "지금 다시 확인해봐"라는 신호뿐이다.

## 목표

같은 계정의 다른 창·탭에서 생긴 변화(새 대화, 제목 변경, 새 메시지, 답변 생성 시작·완료)를 몇 초 안에 반영한다. 지금 보고 있는 대화에서 다른 창이 만든 답변이 생성되는 과정도 실시간으로 볼 수 있게 한다.

## 확정된 설계 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 전달 방식 | 기존 `streaming_service.py`와 같은 패턴(락+큐+구독자 목록)을 **사용자 단위**로 일반화한 새 SSE 채널 | 이미 검증된 패턴을 재사용한다. WebSocket·Redis 같은 새 인프라가 필요 없다 |
| 이벤트 내용 | 데이터를 직접 실어 보내지 않고 "다시 확인해봐"라는 무효화 신호만 보낸다 | 실제 상태 계산(활동 배지 등)은 이미 DB 기준으로 정확하다. 이벤트에 상태를 복제해 담으면 두 곳이 어긋날 위험이 생긴다 |
| 이벤트 종류 | `chats_changed`(사이드바 전체 다시 조회) / `chat_activity`(특정 chatId·branchId 다시 조회, jobId 있으면 그 job 스트림에 붙기) 두 가지로 제한 | 이벤트 종류를 늘릴수록 프론트 쪽 분기와 백엔드 발행 지점이 함께 늘어난다. 두 가지로 실제 필요한 화면(사이드바, 열려 있는 대화)을 모두 커버한다 |
| 다른 창의 실시간 타이핑 | `chat_activity`가 `jobId`를 실어 보내면, 지금 그 대화를 보고 있는 창이 기존 `/ai-response-jobs/{job_id}/stream`에 그대로 붙는다 | 토큰 단위 중계 로직을 새로 만들지 않는다. 이미 있는 걸 한 번 더 쓴다 |
| 기존 폴링 | 없애지 않고 간격만 늘려 안전망으로 남긴다(예: 60초) | SSE 연결이 끊겼다가 재연결 전까지 이벤트를 놓칠 수 있다. 폴링이 그 공백을 메운다 |
| 확장 한계 | 지금은 프로세스 하나짜리 메모리 registry로 간다. 여러 워커·여러 서버로 늘어나면 이 방식은 깨진다 | `docker-compose.yml`에 이미 있지만 지금은 안 쓰는 Redis Pub/Sub이 그때의 자연스러운 다음 단계다. 지금 그 설계까지 하지 않는다 |

## 마일스톤 A · 백엔드 이벤트 채널

새 파일 `backend/app/services/realtime_service.py`. `streaming_service.py`의 구조(락으로 보호된 registry, 구독자별 `queue.Queue`, 하트비트 핑)를 그대로 본뜨되 키를 `job_id`가 아니라 `user_id`로 바꾼다.

- [x] A1. `subscribe(user_id) -> queue.Queue`: 그 사용자의 구독자 목록에 새 큐를 등록하고 돌려준다
- [x] A2. `unsubscribe(user_id, queue)`: 연결이 끊기면 목록에서 뺀다. 구독자가 없어진 사용자는 registry에서 지운다(메모리 누수 방지)
- [x] A3. `publish_chats_changed(user_id)`: 그 사용자의 모든 구독자 큐에 `("chats_changed", {})`를 넣는다
- [x] A4. `publish_chat_activity(user_id, chat_id, branch_id, job_id=None)`: 그 사용자의 모든 구독자 큐에 `("chat_activity", {chatId, branchId, jobId})`를 넣는다
- [x] A5. 큐가 일정 시간(20초) 비어 있으면 하트비트 핑을 보낸다(기존 job 스트림과 같은 이유 — 중간 프록시가 idle 연결을 끊는 것을 막는다). `streaming_service.py`와 달리 서비스 모듈이 아니라 라우터(`realtime.py`)의 SSE 제너레이터 안에 뒀다 — 기존 `stream_ai_response`와 같은 위치다

**완료 기준**: 자동 테스트로 `subscribe` 후 `publish_*`를 호출하면 큐에 이벤트가 들어오고, `unsubscribe` 후에는 들어오지 않는 것을 확인한다.

## 마일스톤 B · 이벤트 발행 지점 연결

새 라우터 `backend/app/routers/realtime.py`. `GET /api/realtime/stream` — `CurrentUser` 의존성으로 인증하고, `realtime_service.subscribe`로 받은 큐를 SSE로 흘려보낸다. 기존 `stream_ai_response`와 같은 형태(`StreamingResponse`, `text/event-stream`).

발행 지점은 아래처럼 최소화한다. 하나하나 새로 찾지 않고, 이미 "무언가 새로 생겼다"를 뜻하는 기존 함수 안에 한 줄씩 추가한다.

- [x] B1. `chat_service.create_chat_with_main_branch`, `create_side_chat`, `create_conversation_node`, `delete_chat`, `update_title` 끝에서 `realtime_service.publish_chats_changed(user_id)`
- [x] B2. `ai_response_service._new_job`(send_message·regenerate·retry_failed_job이 공통으로 거친다) 끝에서 `realtime_service.publish_chat_activity(user_id, chat_id, branch_id, job_id)` — job이 막 시작했다는 신호. 같은 대화를 보고 있는 다른 창이 이 job의 스트림에 붙을 수 있게 한다. `AiResponseJob.id`는 `mapped_column(default=uuid.uuid4)`라 커밋 전엔 비어 있어, `_new_job`에서 id를 직접 만들어 넣도록 고쳤다(구현 중 발견)
- [x] B3. `ai_response_service._run_generation_job`이 `streaming_service.publish_done`을 부르는 바로 다음 줄에서 `realtime_service.publish_chat_activity(user_id, chat_id, branch_id)`(job_id 없이) — 생성이 끝나 DB에 최종 내용이 저장됐으니 다시 조회하라는 신호. 사이드바 배지도 이 시점에 바뀌므로 `publish_chats_changed`도 함께
- [x] B4. `message_service.create_block`은 별도로 건드리지 않는다 — 지금 메시지 생성은 전부 B2의 `send_message` 경로를 거치므로 중복 발행이 된다

**완료 기준**: 새 대화를 만들거나 메시지를 보내면, 같은 계정으로 연결된 다른 SSE 구독자가 해당 이벤트를 받는다(자동 테스트로 두 구독자를 만들어 확인).

- [x] `chats_changed` 수신 시 `loadChats(get().chatListKeyword)` 호출
- [x] `chat_activity` 수신 시, 그 `chatId`·`branchId`가 지금 열려 있는 대화와 같으면 블록·제목을 조용히 다시 불러오고(스크롤 위치·선택 상태는 건드리지 않는다) `reattachGeneratingBlocks()`를 부른다

### C3. 기존 폴링 정리

- [x] `syncChatStatusPolling`의 간격을 2.5초에서 60초로 늘린다. 완전히 없애지는 않는다(연결 끊김 안전망)
- [x] 폴링 시작 조건("생성 중인 게 있어야 켜진다")은 그대로 둔다 — 실시간 이벤트가 주 경로이고, 폴링은 그 이벤트를 놓쳤을 때만 의미가 있다

**완료 기준**: 크롬 창 두 개로 같은 계정에 로그인해, 한쪽에서 새 대화를 만들거나 메시지를 보내면 다른 쪽 사이드바·열려 있는 대화가 몇 초 안에(연결이 살아있다면 거의 즉시) 반영된다. 같은 대화를 양쪽에서 열어두면 한쪽이 보낸 질문의 답변이 다른 쪽에서도 실시간으로 타이핑되듯 보인다.

## 남은 제한 사항

- 우측 사이드 패널(0821_06에서 추가된 `createChatStore` 기반 두 번째 패널)은 이번 실시간 반영 범위에 포함하지 않았다. `chats_changed`는 사이드바(항상 메인 `useChatStore` 기준)만 갱신하고, `chat_activity`도 메인 `useChatStore`의 열린 대화만 본다 — 사이드 패널에서 다른 창의 변화를 실시간으로 보려면 별도 확인이 필요하다
- 대화 제목 자동 변경·삭제 시나리오는 D2 통합 테스트로 발행 지점을 확인했지만, 실제 두 브라우저로 시각 확인하지는 않았다(제목 생성은 실 LLM 키 필요, 삭제는 파괴적 조작이라 이번 라이브 확인에서 생략)
- 계획대로 여러 백엔드 프로세스·서버 간 동기화(Redis Pub/Sub)는 다루지 않았다 — 지금은 프로세스 하나짜리 메모리 registry다

## 위험과 미리 정해둘 것

- **자기 자신이 보낸 이벤트를 다시 처리하지 않게 해야 한다.** 창 A가 메시지를 보내면 창 A 자신도 그 `chats_changed`·`chat_activity`를 받는다. 창 A는 이미 낙관적 업데이트로 화면을 반영했으므로, 이벤트로 또 반영하면 중복 렌더링이나 깜빡임이 생길 수 있다. C2에서 "이미 스트리밍 중이면 중복 연결하지 않는다"고 정한 것과 같은 원칙을, 사이드바 재조회 쪽에도 적용해야 한다 — `loadChats`는 멱등적(다시 불러도 같은 결과)이라 중복 호출 자체는 안전하지만, 매번 전체 목록을 새로 렌더링하면서 깜빡이지 않는지는 확인이 필요하다.
- **여러 탭이 같은 계정으로 동시에 접속하면 구독자 수만큼 이벤트가 팬아웃된다.** 사용자 한 명이 탭을 10개 열어두는 극단적인 경우까지 최적화하지 않는다. 실제 사용 패턴(두세 개)을 기준으로 한다.
- **SSE 연결 하나가 오래 유지되므로, 서버가 재시작되면 모든 연결이 끊긴다.** 프론트의 지수 백오프 재연결이 이 상황을 자연스럽게 복구해야 한다. 재연결 직후에는 놓쳤을 이벤트를 보정하기 위해 `loadChats`를 한 번 강제로 호출한다.
- **이 채널을 열어두는 것 자체가 백엔드 연결 수를 늘린다.** 로그인한 사용자 수만큼 상시 연결이 늘어난다. 로컬 개발·소규모 배포에서는 문제가 아니지만, 위 "확장 한계" 항목과 같은 맥락에서 기록해 둔다.

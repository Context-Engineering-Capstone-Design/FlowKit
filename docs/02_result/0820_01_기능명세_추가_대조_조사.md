# 0820_01 기능명세 추가 대조 조사

- 상태: 조사 완료 (구현 계획 아님)
- 기준 커밋: `8a70cbae67088b073f645b27b779aaa60ccf47f3`
- 주의: 조사 중 다른 세션이 같은 저장소를 고치고 있었다. 아래 항목은 모두 조사 마지막에 현재 작업 트리 파일로 다시 확인했고, 그 시점에 여전히 남아 있던 것만 적었다.

## 목표

`기획 문서/`의 AI·BE·FE 기능명세서를 코드와 다시 하나씩 대조해서, 명세에는 있는데 코드에 없거나 다르게 동작하는 부분을 찾는다. 이 문서는 조사 결과이며 구현 계획이 아니다.

## 범위

- 명세: `AI기능명세서` 5개, `BE기능명세서` 11개, `FE기능명세서` 11개 문서의 기능 ID 174개 전부
- 코드: `backend/app` 전체, `modeling` 전체, `frontend/src` 전체
- 제외: `docs/01_plan/0819_09_기능명세_대조_미구현_조사.md`에 이미 적힌 항목 전부(해결된 것 포함)
- 제외: `docs/02_result/0819_11`이 다루는 중간 우선순위 8개 항목

## 조사 방법

1. 기능 ID마다 명세의 처리 내용·출력 항목·오류 처리를 읽고, 대응하는 코드를 찾아 비교했다.
2. 화면 기능은 버튼에서 시작해 store 함수와 서버 호출까지 실제 실행 순서를 따라갔다.
3. 의심스러운 항목은 백엔드에 임시 테스트를 만들어 직접 실행해 재현했다. 확인 후 임시 테스트 파일은 삭제했다.
4. 기준 상태 확인: 백엔드 자동 테스트 164개, 프론트엔드 31개가 모두 통과한다. 즉 아래 문제들은 현재 자동 테스트로 걸러지지 않는다.

## 상 우선순위

### 1. [BE-AIRESP-004·006 / FE-BRANCH-002·007] 하위 브랜치에서 이어받은 AI 답변의 평가 조회가 실패해, 브랜치 생성과 전환이 오류로 보인다

- 명세: BE-AIRESP-006은 평가·재생성 권한을 확인할 때 "블록이 그 브랜치와 채팅에 속하는지, AI 답변인지, 채팅 주인이 맞는지"만 보라고 한다.
- 코드: 평가 조회·저장이 [`ai_response_service.py`](../../backend/app/services/ai_response_service.py)의 `_require_assistant_block` → `get_editable_block`을 쓴다. 이 함수는 **그 브랜치가 직접 만든 블록만** 통과시킨다. 하위 브랜치 화면에 보이는 '이어받은' 답변은 부모 브랜치 소유라 거절된다.
- 재현(임시 테스트로 직접 확인): 질문 1개와 답변 1개를 만든 뒤 그 답변을 분기 지점으로 브랜치를 만들고, 새 브랜치에서 그 답변의 평가를 조회하면 400 오류가 난다. 오류 문구는 "다른 브랜치에서 이어받은 메시지는 이 브랜치에서 수정할 수 없습니다"이다. 평가 저장과 답변 재생성도 같다.
- 영향: 화면이 브랜치를 열 때마다 보이는 AI 답변 전부의 평가를 한꺼번에 조회한다([`chatStore.ts`](../../frontend/src/store/chatStore.ts)의 `refreshFeedbacks`). 하나라도 실패하면 전체가 실패로 처리되기 때문에,
  - 브랜치를 만들면 서버에는 정상적으로 만들어지는데도 화면은 실패로 보고 **브랜치 생성 모달이 닫히지 않고 오류 배너가 뜬다**(`createBranch`가 `switchBranch` 결과를 성공 여부로 쓴다).
  - 사이드바에서 하위 브랜치를 눌러도 같은 오류 배너가 뜬다.
  - 이어받은 AI 답변에도 좋아요·싫어요·답변 다시 시도 버튼이 그대로 보이는데, 누르면 같은 오류가 난다.
- 참고: 평가는 대화 내용을 전혀 바꾸지 않으므로 '수정 금지' 검사를 적용할 이유가 없다. 답변 재생성은 내용을 바꾸므로 별도 판단이 필요하다(아래 판단 항목 참고).
- 우선순위: 상

### 2. [BE-REFINE-005 / BE-MSG-004] 하위 브랜치에서 이어받은 블록의 정제를 승인하면 원본 브랜치의 대화가 바뀐다

- 명세·근거: BE-MSG-004는 "새 브랜치를 만들지 않고 같은 브랜치 내 활성 버전만 변경한다"고 정하고, 요구사항 REQ-019는 "원본 대화는 유지"를 수용 기준으로 둔다. 코드도 직접 수정 경로에서는 이어받은 블록의 수정을 막는다.
- 코드: [`refine_service.py`](../../backend/app/services/refine_service.py)의 `approve`가 대상 블록을 브랜치 확인 없이 그대로 가져와 새 버전을 만들고 활성 버전으로 바꾼다(222행 부근). 정제 대상 선택 검사도 '화면에 보이는 블록'만 보므로 이어받은 블록이 그대로 통과한다.
- 재현(임시 테스트로 직접 확인): 하위 브랜치에서 이어받은 AI 답변을 정제하고 승인하면, Main 브랜치를 다시 조회했을 때 그 답변 내용이 정제본으로 바뀌어 있다.
- 영향: 사용자는 하위 브랜치에서만 정리했다고 생각하는데 원본 대화가 조용히 바뀐다. 직접 수정은 막혀 있어서, 같은 블록에 대해 두 경로의 규칙이 서로 다르다.
- 우선순위: 상

## 중 우선순위

### 3. [FE-INPUT-006] 메시지 전송이 실패하면 입력 내용과 첨부 목록이 사라진다

- 명세: 전송 실패 시 입력 내용과 첨부 목록을 되살려 다시 보낼 수 있게 한다.
- 코드: [`chatStore.ts`](../../frontend/src/store/chatStore.ts)의 `sendMessage`가 실패하면 대화를 다시 불러오는데, 그 안의 `applyDetail`이 입력창 내용과 첨부 목록을 함께 비운다.
- 영향: 모델을 부르다 실패한 경우에는 질문이 서버에 남아 '다시 시도' 버튼으로 이어갈 수 있어 영향이 작다. 하지만 질문이 저장되기 **전에** 나는 오류(지원하지 않는 모델, 첨부 파일 문제, Context 블록 없음, 연결 실패·시간 초과)에서는 질문이 서버에도 없고 입력창도 비워져, 사용자가 쓴 내용이 완전히 사라진다. 첨부 미리보기용 메모리(objectURL)도 이 경로에서는 해제되지 않는다.
- 우선순위: 중

### 4. [FE-NOTIFY-005 / AI-CORE-005] 화면의 요청 제한 시간(30초)이 서버의 모델 응답 제한(60초)보다 짧다

- 코드: 화면의 모든 서버 요청은 30초에서 끊긴다([`client.ts`](../../frontend/src/api/client.ts) 38행, [`requestTimeout.ts`](../../frontend/src/lib/requestTimeout.ts) 1행). 반면 모델 호출 제한은 60초다([`modeling/config.py`](../../modeling/config.py)의 `REQUEST_TIMEOUT_SECONDS`).
- 영향: 답변 생성이 30초를 넘기면 화면만 실패로 처리한다. 서버는 계속 진행해 답변을 저장할 수 있어, 사용자는 "요청 시간이 초과되었습니다" 안내를 받고도 대화에는 답변이 남는 어긋난 상태를 본다. 블록별 정제는 블록마다 모델을 부르므로 30초를 넘길 여지가 더 크다.
- 우선순위: 중

### 5. [FE-AIRESP-001] 전송 직후 질문 블록과 '생성 중' 답변 블록을 만들지 않는다

- 명세: 보낸 질문을 사용자 블록으로 먼저 추가하고, 바로 아래에 AI 블록을 '생성 중' 표시와 함께 만든다. 응답을 받으면 그 자리를 실제 답변으로 바꾼다.
- 코드: [`ChatArea.tsx`](../../frontend/src/components/ChatArea.tsx)는 목록 맨 아래에 "답변을 쓰는 중…" 문구 한 줄만 띄우고, 질문·답변 블록은 서버 응답을 받은 뒤에야 함께 추가한다.
- 영향: 답변을 기다리는 동안 자기가 방금 보낸 질문이 대화에 보이지 않는다. 기다리는 시간이 길수록 전송이 됐는지 알기 어렵다.
- 우선순위: 중

### 6. [FE-BRANCH-006] Context 패널에 '이 Context로 브랜치 생성' 버튼이 없다

- 명세: 브랜치 생성 모달을 여는 경로는 두 가지다. 브랜치 생성 버튼과 **Context 패널의 '이 Context로 브랜치 생성'**.
- 코드: [`ContextPanel.tsx`](../../frontend/src/components/ContextPanel.tsx)의 패널 하단에는 '이 Context로 질문하기' 버튼만 있다(384~390행). 해당 영역 주석은 "Context 적용과 브랜치 생성"이라고 적혀 있어 원래 있어야 할 버튼이 빠진 것으로 보인다.
- 영향: 블록을 골라 놓고 그 선택을 그대로 브랜치로 넘기는 흐름이 끊긴다. 지금은 헤더의 브랜치 생성 버튼이나 블록의 '분기' 버튼으로 돌아가야 한다(선택한 블록은 모달에 그대로 넘어가므로 결과는 같다).
- 우선순위: 중

### 7. [BE-AUTH-001·009] 로그아웃해도 그때까지 쓰던 인증 토큰이 만료 전까지 계속 통한다

- 명세: BE-AUTH-001은 토큰과 **세션**을 검증하고, 유효하지 않은 세션은 오류로 처리한다고 적혀 있다. BE-AUTH-009는 현재 세션을 만료 처리한다.
- 코드: 로그아웃은 재발급 토큰만 무효화한다([`auth_service.py`](../../backend/app/services/auth_service.py)의 `logout`). 인증 토큰 검증은 서명과 만료만 보고 세션을 확인하지 않는다([`deps.py`](../../backend/app/deps.py)).
- 재현(직접 확인): 로그아웃한 뒤에도 같은 인증 토큰으로 `/api/auth/me`가 200을 주고, `/api/auth/status`가 "로그인 상태"로 답한다. 재발급만 401이다.
- 영향: 화면은 토큰을 지우므로 본인 기기에서는 정상적으로 로그아웃된다. 다만 토큰이 이미 유출·복사된 경우 로그아웃으로 끊을 수 없고, 최대 30분(`access_token_expire_minutes`) 동안 유효하다. 명세가 말하는 "유효하지 않은 세션" 오류는 현재 구조에서는 발생할 수 없다.
- 우선순위: 중

### 8. [FE-REFINE-005] 이미 처리된 정제 결과라는 응답을 받아도 화면을 다시 맞추지 않는다

- 명세: 승인 실패 시 오류를 표시하고, "이미 처리된 결과"라는 응답을 받으면 최신 상태를 다시 조회해 화면을 맞춘다.
- 코드: [`chatStore.ts`](../../frontend/src/store/chatStore.ts)의 `approveResult`·`rejectResult`는 실패하면 오류 문구만 저장하고 정제 작업 상태를 다시 불러오지 않는다.
- 영향: 다른 창이나 중복 클릭으로 이미 처리된 항목이 화면에는 '대기'로 남아, 눌러도 계속 같은 오류만 반복된다.
- 우선순위: 중

## 하 우선순위

### 9. [BE-AUTH-009] 로그아웃이 현재 세션만이 아니라 모든 기기의 세션을 끊는다

- 명세는 "현재 인증 세션을 종료"라고 적혀 있는데, 코드는 그 사용자의 모든 재발급 토큰을 무효화한다. 다른 기기에서 로그인 중이면 함께 끊긴다. 인증 토큰에 세션 구분 값이 없어서, 고치려면 7번과 함께 다뤄야 한다.

### 10. [FE-INPUT-004] 웹 검색을 켜고 끌 때 알림이 뜨지 않는다

- 명세는 "바뀐 상태를 알리는 짧은 알림을 표시"를 요구한다. 코드는 값만 바꾼다([`chatStore.ts`](../../frontend/src/store/chatStore.ts)의 `setWebSearchEnabled`). 0819_09가 적은 '미지원 오류 시 자동 해제'와는 다른 부분이다.

### 11. [FE-BRANCH-004] 대화 열기로 하위 브랜치에 들어가면 출발 Context 요약이 비어 있다

- 채팅 상세 조회 응답(BE-CHAT-005)에는 출발 Context 정보가 없고, 화면도 이때 그 값을 빈 목록으로 초기화한다. 지금은 전송 실패 후 화면을 다시 맞출 때만 이 경로를 타므로, 그 뒤 브랜치 상단의 Context pill 목록이 사라진다. 브랜치 목록에서 다시 들어가면 정상 표시된다.

### 12. [FE-USERSET-007] 피드백 유형이 버튼 묶음이 아니라 드롭다운이고, 기본값이 미리 선택돼 있다

- 명세는 유형 버튼을 나열하고 "유형 선택 여부"를 검증하라고 한다. 코드는 드롭다운에 '사용성 불편'이 기본 선택돼 있어([`FeedbackModal.tsx`](../../frontend/src/components/FeedbackModal.tsx)) 미선택 상태 자체가 없다.

### 13. [FE-USERSET-004] API 키 삭제 확인이 앱 공통 확인 창이 아니라 브라우저 기본 확인 창이다

- [`ApiKeyModal.tsx`](../../frontend/src/components/ApiKeyModal.tsx)가 `window.confirm`을 쓴다. 앱에는 공통 확인 창([`ConfirmDialog.tsx`](../../frontend/src/components/ConfirmDialog.tsx))이 있고 대화 삭제는 그것을 쓴다. 일부 브라우저 설정에서는 기본 확인 창이 막힐 수 있다.

### 14. [FE-MSG-005·006·008, FE-CTXEDIT-005, FE-AIRESP-002] 블록의 '더보기 메뉴'가 없다

- 명세는 복사·직접 수정·여기서 브랜치 생성·AI 편집 지시·답변 다시 시도를 더보기 메뉴에서도 열 수 있다고 적는다. 코드는 [`MessageBlockActions.tsx`](../../frontend/src/components/MessageBlockActions.tsx)에 아이콘 버튼을 나란히 둔다. 기능은 모두 있으나 화면 구성이 다르다.

### 15. [FE-MSG-006] 수정 모드에 들어가도 입력창에 커서가 가지 않는다

- 명세는 "현재 내용을 채운 뒤 커서를 옮긴다"까지 요구한다. [`MessageEditForm.tsx`](../../frontend/src/components/MessageEditForm.tsx)에는 자동 포커스가 없다.

### 16. [FE-AIRESP-004] 좋아요·싫어요 표시가 서버 응답을 받은 뒤에 바뀐다

- 명세 비고는 "버튼 표시는 즉시 바꾸고 저장은 뒤이어 처리한다"이다. 코드는 저장이 끝난 뒤 표시를 바꾼다. 실패 시 되돌릴 상태가 없으므로 동작 자체는 안전하다.

### 17. [FE-REFINE-002] 정제 미리보기 항목에 블록 식별값이 없다

- 명세는 항목마다 블록 식별값·역할 배지·상태 배지를 위에 표시하라고 한다. [`ContextPanel.tsx`](../../frontend/src/components/ContextPanel.tsx)는 역할과 상태만 보여준다.

### 18. [BE-INPUT-002] 기한이 지난 임시 첨부를 정리하는 코드가 어디에서도 실행되지 않는다

- [`input_assist_service.py`](../../backend/app/services/input_assist_service.py)에 `cleanup_expired`가 있지만 부르는 곳이 없다. 전송에 쓰이지 않은 첨부 파일과 원본이 계속 남는다. 명세가 실행 주기를 정하지는 않았다.

### 19. [AI-CORE-004] 요청에 키가 없으면 모듈에 남은 예비 키나 환경변수 키를 대신 쓴다

- 명세는 "키를 모듈 안에 남겨 두거나 다음 요청에 재사용하지 않는다"고 못박는다. [`modeling/llm.py`](../../modeling/llm.py)의 `resolve_api_key`는 요청 키가 없으면 `configure()`로 저장한 예비 키, 그다음 환경변수 `GOOGLE_API_KEY`를 쓴다. 지금 백엔드는 항상 사용자 키를 넘기고 없으면 먼저 오류를 내므로 실제 영향은 없지만, 모델링 패키지를 단독으로 쓰면 다른 키로 조용히 호출된다.

### 20. [BE-AIRESP-005] AI 실패 오류 코드가 명세와 다르고, 분류가 예외 이름 글자에 의존한다

- 명세의 오류 코드는 `AI_TIMEOUT`, `AI_RESPONSE_EMPTY`, `AI_PROVIDER_ERROR`, `RATE_LIMITED`인데 코드는 한도 초과를 `AI_RATE_LIMITED`로 돌려준다. 또 분류를 예외 클래스 이름에 'timeout'·'rate'·'quota'가 들어 있는지로 판단해서([`ai_response_service.py`](../../backend/app/services/ai_response_service.py)의 `_classify_error`), 공급자가 다른 이름을 쓰면 전부 `AI_PROVIDER_ERROR`가 된다.

### 21. [BE-NOTIFY-002] 오류 응답에 심각도(severity) 값이 없다

- 명세 출력은 `errorCode, message, severity`인데 응답에는 `errorCode, message, detail, traceId`만 있다. 화면이 심각도로 표시를 나누지는 않으므로 지금 영향은 없다.

### 22. [BE-MSG-001] 메시지 블록 생성 요청에 `sourceType`을 넣을 수 없다

- 명세 입력에는 `sourceType`이 있으나 요청 형식에는 없고 서버가 항상 '원본'으로 고정한다. 이 API는 현재 화면에서 쓰지 않는다.

### 23. 쓰이지 않는 코드: 활동 시각 갱신 함수

- BE-CHAT-007의 활동 시각 갱신은 메시지 생성·버전 추가·브랜치 생성 안에서 각각 처리되고 있어 기능은 충족한다. 다만 [`chat_service.py`](../../backend/app/services/chat_service.py)의 `touch_activity`는 아무 곳에서도 부르지 않는다.

# 0820_08 사이드 채팅 트리와 선택적 메인 반영

- 상태: 구현 완료
- 기준: 2026-08-20 논의
- 관련 기능: 채팅 탭, 브랜치, Context 관리

## 목표

부모 메인 채팅의 공통 컨텍스트를 활용하면서도, 별도 흐름으로 탐색할 수 있는 사이드 채팅을 제공한다. 사이드 채팅의 결과는 메인 채팅에 자동 반영하지 않고 사용자가 필요한 경우에만 반영한다.

## 확정된 구조

### 대화 세션과 탭

- 메인 채팅과 사이드 채팅은 모두 별도 탭으로 유지한다.
- 탭 구조에서는 메인·사이드 채팅이 동등한 대화 세션이다.
- 역할만 다르다. 메인 채팅은 공통 컨텍스트의 부모이고, 사이드 채팅은 부모 컨텍스트를 자동 참고하는 자식 대화다.
- 새 사이드 채팅을 열어도 기존 탭은 화면 위치를 바꾸지 않고 그대로 남긴다.
- 메인 채팅뿐 아니라 사이드 채팅도 자식 사이드 채팅을 만들 수 있다. 새 자식도 별도 탭으로 유지한다.
- 사용자가 삭제하기 전까지 사이드 채팅은 일반 채팅처럼 보존한다.

### 트리 관리

- 좌측 사이드 채팅 관리 패널에서 사이드 채팅의 생성 관계를 Git 브랜치 그래프처럼 보여준다.
- 그래프의 노드를 선택하면 해당 대화 세션 탭을 열거나 활성화한다.
- 각 사이드 채팅이 생성된 부모 대화 흐름의 시점에는 저장·불러오기 버튼을 제공한다. 사용자는 부모 대화를 따라가며 그 시점에서 연결된 사이드 채팅을 찾을 수 있다.
- 사이드 채팅에서 만든 자식은 그래프에서 해당 사이드 채팅 아래에 연결한다.

### 컨텍스트와 대화 흐름

- 새 사이드 채팅은 부모 메인 채팅 전체를 자동으로 참고한다.
- 사이드 채팅 생성 시에는 부모의 최신 대화 흐름 전체를 시작 맥락으로 사용하고, 그 생성 시점을 부모 대화 안에 기록한다.
- 부모 메인 채팅에 새 메시지가 추가되면, 자식 사이드 채팅도 새 내용을 자동 참고한다.
- 사이드 채팅은 공통 컨텍스트와 별도로 자신만의 대화 흐름을 가진다.
- 사이드 채팅에서 자식 사이드 채팅을 만들더라도, 자식은 루트 메인 채팅의 공통 컨텍스트만 자동 참고한다. 부모 사이드 채팅의 메시지·답변은 자동 참고하지 않는다.
- 따라서 사이드 채팅끼리는 부모·자식 관계여도 서로의 메시지나 답변을 자동 참고하지 않는다.
- 과거 사이드 답변이 생성된 당시의 컨텍스트 스냅샷은 저장하지 않는다.

### 메인 채팅 반영

- 사이드 채팅은 기본적으로 메인 채팅을 변경하지 않는다.
- 사용자는 사이드 채팅의 결과를 선택해 다음 작업을 실행할 수 있다.
  - 답변 일부 또는 전체를 Context로 추가
  - 질문·답변을 메인 채팅 메시지로 가져오기
  - 새 브랜치 생성
- 사이드 채팅에서 새 브랜치를 만들면, 해당 브랜치는 사이드 채팅과 같은 부모 아래의 형제 브랜치로 생성한다. 기존 부모와 자식 관계를 공유한다.

### 완료 항목

- **A**: `Chat` 모델에 `kind`(MAIN/SIDE), 구조적 부모(`parentChatId`/`parentBranchId`/`parentMessageBlockId`), 공통 컨텍스트 근거인 루트 메인 채팅(`rootChatId`/`rootBranchId`)을 추가했다(`backend/app/models/chat.py`, 마이그레이션 `a81911side`). 자식 사이드 채팅은 중간 부모를 거치지 않고 항상 최상위 메인을 직접 참조해 "사이드 채팅끼리는 서로의 흐름을 자동 참고하지 않는다"를 만족한다. 생성·자식 목록·트리 조회 API(`backend/app/routers/side_chat.py`)를 추가했고, 이름 변경·삭제·상세 조회는 기존 채팅 API를 그대로 재사용한다. AI 답변 생성 시 사이드 채팅이면 전송할 때마다 루트 메인 채팅의 최신 흐름을 다시 읽어 답변 입력 앞에 붙인다(`ai_response_service.py`) — 스냅샷을 저장하지 않으므로 부모에 새 메시지가 쌓이면 자동 반영된다.
- **B**: `chatStore`에 탭 상태(`tabs`, `activeTabId`)를 추가했다. 활성 탭의 실제 대화 상태(블록·브랜치 등)는 기존 singleton 필드를 그대로 쓰고, 비활성 탭은 채팅 id·브랜치·제목만 가벼운 캐시로 들고 있다가 다시 열릴 때 서버에서 새로 불러온다 — 기존 Context·AI 응답 로직은 건드리지 않았다. `ChatTabBar`(탭 전환·닫기), `ContextPanel`의 "사이드 채팅" 섹션(새 사이드 채팅 만들기·기존 자식으로 전환), 좌측 `Sidebar`의 "사이드 채팅" 트리 섹션(루트 메인 아래 생성 관계를 들여쓰기 목록으로 표시, 클릭해 이동), `MessageBlockItem`의 "여기서 사이드 채팅 만들기" 버튼과 연결된 사이드 채팅을 여는 칩을 추가했다.
- **C**: 사이드 채팅은 기본적으로 부모를 바꾸지 않으며, 사용자가 명시적으로 고른 결과만 세 가지 방식으로 반영된다. Context로 추가는 기존 파이프라인(`contextBlockIds` → `context_service.build_snapshot`)을 그대로 재사용하되, 같은 사이드 채팅 트리(루트 메인 + 모든 사이드)에 속한 블록이면 지금 브랜치에 없어도 소스로 허용하도록 확장했다. 메시지로 가져오기는 새 서비스(`side_chat_service.import_blocks_as_messages`)와 엔드포인트(`POST .../import-blocks`)로 선택한 블록을 부모 브랜치에 실제로 복사한다(원본은 그대로 남는다). 형제 브랜치 생성은 기존 브랜치 생성 API를 그대로 썼다 — 사이드 채팅이 갈라져 나온 지점(`parentBranchId`/`parentMessageBlockId`)을 기준·분기점으로 삼고 선택한 블록 내용을 `editedBaseContent`로 넘기면 그 지점의 형제 브랜치가 되므로 백엔드 변경이 필요 없었다. 세 동작 모두 실행 후 부모 탭으로 전환해 결과를 바로 보여준다.
- **D**: 위 항목대로 백엔드·프론트엔드 자동 테스트를 작성했고, 아래 "검증 결과"에 정리한 대로 로컬 브라우저에서 실제 OpenAI 응답까지 포함해 전체 흐름(메인 채팅 생성 → 사이드 채팅 생성 → 부모 메시지 자동 참고 → 탭 전환 → Context 추가/메시지 가져오기/형제 브랜치 생성)을 확인했다.

### 남은 제한 사항

- **B3 트리 시각화**: "Git 브랜치 그래프처럼"을 문자 그대로 구현하지 않았다. 부모·자식 관계는 들여쓰기와 종류별 아이콘(메인/사이드)으로 표시하는 단순 목록이며, 실제 그래프 선·분기 연결선은 그리지 않는다.
- **C3 형제 브랜치 내용**: 선택한 여러 블록을 합쳐 넣지 않고, 그중 가장 최근(마지막) 블록 하나의 내용만 새 브랜치의 시작 내용으로 쓴다.
- **탭 상태의 새로고침 유지**: 열린 탭 목록은 화면 상태로만 존재하고 새로고침하면 초기화된다(기존 앱도 대화 자체를 새로고침 시 복원하지 않는 동일한 방식이라 이번에 새로 생긴 제한은 아니다).
- **브라우저 검증은 수동 확인**: Playwright 등 자동화된 E2E는 만들지 않았다. 이번 세션에서 크롬 원격 디버깅으로 직접 확인했다.
- **삭제 시 자손 재연결 안 함**: 중간 사이드 채팅을 삭제하면 그 자식들은 트리에서 `parentChatId`가 끊겨 뜨게 된다(데이터는 보존되고 `sideChatTree`에는 계속 나타나지만, 삭제된 채팅 아래 중첩 표시는 사라진다). 조부모로 재연결하지 않는다 — 계획 문서에 명시되지 않은 엣지 케이스라 단순하게 처리했다.

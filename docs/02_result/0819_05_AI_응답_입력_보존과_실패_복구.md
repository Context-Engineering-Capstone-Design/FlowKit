## 목표

AI 답변이 처음 만들어질 때 사용한 비밀값 제외 입력을 스냅샷으로 보존한다. 재생성은 현재 대화를 다시 계산하지 않고 해당 스냅샷을 그대로 사용한다. 생성·재생성 작업의 진행·성공·실패 상태를 DB와 화면에서 추적하고 다시 시도할 수 있게 한다.

## 대상 기능

- AI-ANSWER-004
- BE-AIRESP-001~003, 005
- FE-AIRESP-001·002

## 현재 명세 충돌

현재 `backend/app/services/ai_response_service.py`의 재생성은 다음 순서로 동작한다.

1. 현재 브랜치의 활성 메시지 흐름을 다시 읽는다.
2. 대상 답변 바로 앞의 사용자 질문을 찾는다.
3. 적용 Context는 빈 목록으로 둔다.
4. 현재 흐름에서 만든 입력으로 새 버전을 생성한다.

AI-ANSWER-004는 최초 답변 생성 때의 질문, 흐름, Context, 모델, 검색 설정을 그대로 사용하도록 정한다. 현재 구현은 Context를 버리고 흐름을 다시 계산하므로 같은 답변의 버전끼리 입력 조건이 달라지는 명세 충돌이다.

## 확정 구현 방식

### 동기 API 유지

- 현재처럼 HTTP 요청 안에서 모델 호출을 마친다.
- Redis 작업 큐와 별도 Worker는 도입하지 않는다.
- DB의 작업 상태는 입력 보존·실패 추적·재시도 기준으로 사용한다.

### 스냅샷 범위

저장 항목:

- 사용자 질문 본문
- 최초 생성 시점의 활성 메시지 흐름과 역할
- 적용 Context의 본문·원본 블록·버전
- 선택 모델 ID
- 웹 검색 사용 여부
- 첨부 ID와 첨부 순서
- 요청 종류: 최초 생성 또는 재생성

저장하지 않는 항목:

- 사용자 API 키 원문·암호문
- 파일 바이트
- Provider 내부 오류 원문

재생성 때 API 키는 같은 사용자의 현재 등록 키를 다시 조회한다. 키는 비밀값이므로 입력 스냅샷에 저장하지 않는다.

### 첨부 보존

- 연결된 첨부는 메시지와 함께 보존한다.
- 재생성은 스냅샷의 첨부 ID로 저장소 원본을 다시 읽는다.
- 첨부가 운영 정책으로 삭제돼 원본이 없으면 `AI_INPUT_SNAPSHOT_INCOMPLETE`로 실패한다. 첨부를 빼고 조용히 재생성하지 않는다.

### 과거 답변 호환

- 마이그레이션 이전 AI 답변에는 작업·스냅샷이 없다.
- 이 경우에만 기존 방식으로 직전 사용자 질문과 당시 확인 가능한 흐름을 구성한다.
- 과거 답변의 Context는 `AppliedContextLog`가 있으면 복원한다.
- 복원할 수 없는 값은 기본값을 쓰지 않고 화면에 `과거 답변이라 일부 조건을 복원할 수 없음`을 알린다.
- 신규 답변에는 호환 경로가 절대 사용되지 않도록 테스트한다.

## 데이터 구조

### `AIResponseJob`

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| `id` | UUID | 작업 ID |
| `user_id` | UUID | 요청 사용자 |
| `chat_id` | UUID | 소속 채팅 |
| `branch_id` | UUID | 소속 브랜치 |
| `user_message_block_id` | UUID | 원래 질문 블록 |
| `assistant_message_block_id` | UUID 또는 null | 성공 후 답변 블록 |
| `result_version_id` | UUID 또는 null | 성공 후 생성 버전 |
| `source_job_id` | UUID 또는 null | 재생성의 원본 작업 |
| `job_type` | enum | `generate`, `regenerate` |
| `status` | enum | `requested`, `completed`, `failed` |
| `input_snapshot` | JSON | 비밀값을 제외한 고정 입력 |
| `error_code` | 문자열 또는 null | 표준 오류 코드 |
| `error_message` | 문자열 또는 null | 사용자용 안전 문구 |
| `created_at`, `updated_at` | 시각 | 공통 이력 |

### 입력 스냅샷 예시

```json
{
  "schemaVersion": 1,
  "userPrompt": "표로 정리해줘",
  "messageFlow": [
    { "role": "user", "content": "이전 질문" },
    { "role": "assistant", "content": "이전 답변" }
  ],
  "appliedContext": [
    {
      "blockId": "uuid",
      "versionId": "uuid",
      "content": "선택한 내용",
      "orderIndex": 0
    }
  ],
  "selectedModelId": "gemini-model-id",
  "webSearchEnabled": false,
  "attachmentIds": []
}
```

`schemaVersion`을 두어 필드가 늘어날 때 과거 스냅샷을 구분한다.

## 생성 흐름

1. 사용자·채팅·브랜치·질문·Context·모델·검색·첨부를 검증한다.
2. 사용자 메시지 블록과 첨부 연결을 저장한다.
3. 확정된 입력 스냅샷으로 `AIResponseJob(requested)`를 만든다.
4. 사용자 메시지와 작업을 먼저 커밋한다.
5. 사용자 키를 조회해 스냅샷을 `AnswerRequest`로 복원한다.
6. 모델을 호출한다.
7. 성공하면 assistant 블록과 첫 버전을 저장하고 작업을 `completed`로 바꾼다.
8. 실패하면 질문은 유지하고 작업을 `failed`로 바꾼 뒤 표준 오류를 반환한다.

작업 생성 전 검증 실패는 `AIResponseJob`을 만들지 않는다. 작업 생성 후 모델 호출 실패만 실패 작업으로 남긴다.

## 재생성 흐름

1. 대상이 현재 사용자 채팅의 assistant 블록인지 확인한다.
2. 대상의 최초 생성 작업을 찾는다.
3. 최초 작업의 `input_snapshot`을 읽는다.
4. 첨부·Context 참조가 아직 유효한지 확인한다.
5. 현재 사용자 API 키만 새로 조회한다.
6. 같은 입력 스냅샷을 가진 `regenerate` 작업을 만든다.
7. 성공하면 기존 assistant 블록에 새 버전을 추가하고 활성화한다.
8. 실패하면 기존 본문과 활성 버전을 그대로 두고 작업만 `failed`로 남긴다.

재생성의 재생성도 직전 재생성 작업이 아니라 최초 생성 작업의 스냅샷을 사용한다. 버전마다 입력 조건이 연쇄적으로 달라지는 것을 막기 위해서다.

## API 계약

### 메시지 전송 성공

기존 응답에 다음 값을 추가한다.

- `aiResponseJobId`
- `jobStatus: "completed"`
- 마일스톤 2의 모델·검색·첨부·검색 근거 정보

### 메시지 전송 실패

표준 오류의 `detail`에 다음 안전 정보만 포함한다.

```json
{
  "aiResponseJobId": "uuid",
  "userMessageBlockId": "uuid",
  "retryable": true
}
```

내부 예외 원문은 넣지 않는다.

### 답변 재생성

기존 경로를 유지한다.

`POST /api/chats/{chatId}/branches/{branchId}/blocks/{blockId}/regenerate`

응답에 `aiResponseJobId`와 새 버전 정보를 추가한다.

### 최초 생성 실패 재시도

`POST /api/chats/{chatId}/branches/{branchId}/ai-response-jobs/{jobId}/retry`

- 실패 상태인 생성 작업만 허용한다.
- 사용자 메시지를 새로 만들지 않는다.
- 기존 스냅샷으로 새 작업을 만들고 성공 시 assistant 블록을 생성한다.
- 같은 실패 작업을 동시에 두 번 재시도하지 못하게 한다.

## FE 상태 전이

### 최초 생성

1. 전송 즉시 임시 사용자 블록을 표시한다.
2. 바로 아래 임시 AI 블록에 `생성 중`을 표시한다.
3. 성공하면 서버 블록으로 두 임시 블록을 교체한다.
4. 실패하면 서버에서 채팅을 다시 읽어 저장된 사용자 블록을 맞춘다.
5. 사용자 블록 아래에 실패 안내와 다시 시도 버튼을 표시한다.

### 재생성

1. 기존 답변 본문은 유지한다.
2. 대상 블록에만 반투명 진행 상태와 버튼 비활성화를 적용한다.
3. 성공하면 새 본문·버전 위치를 반영한다.
4. 실패하면 기존 본문·버전 위치를 그대로 유지하고 오류를 표시한다.

전역 `isSending` 하나로 모든 답변 블록을 막지 않는다. `pendingByBlockId`와 최초 생성 작업 상태를 분리한다.

- [ ] 최초 생성 스냅샷에 질문·흐름·Context·모델·검색·첨부가 들어간다.

- [ ] Context가 있으면 최초 생성과 재생성의 입력이 완전히 같다.

- [ ] 재생성 시 현재 브랜치에 새 메시지가 생겨도 입력이 바뀌지 않는다.
- [ ] 재생성 성공은 같은 블록의 새 버전을 만든다.
- [ ] 재생성 실패는 활성 버전을 바꾸지 않는다.
- [ ] 최초 생성 실패는 질문과 실패 작업을 남긴다.

- 입력 조건을 바꾼 별도 답변 생성. 조건을 바꾸려면 새 질문으로 처리한다.

## 주의사항

- `AppliedContextLog`는 현재 사용자 메시지 블록과 연결된다. 재생성 대상 assistant 블록의 직전 사용자 블록을 정확히 연결해야 한다.
- 답변 생성 실패 뒤 질문은 이미 커밋돼 있다. 트랜잭션을 합쳐 질문까지 되돌리지 않는다.
- 스냅샷 JSON 형식을 바꾸면 `schemaVersion`별 복원 테스트를 먼저 추가한다.

## 구현 결과

- `AIResponseJob`과 입력 스냅샷을 추가했다. 신규 생성·재생성·실패 재시도는 질문, 흐름, Context, 모델, 검색, 첨부 ID를 같은 스냅샷으로 사용한다.
- 생성 실패는 사용자 질문과 실패 작업을 남기며, 안전한 작업 ID·질문 블록 ID·재시도 가능 여부만 오류 상세에 반환한다.
- 실패한 최초 생성 작업은 같은 질문 블록을 재사용해 다시 시도한다. 재생성은 기존 답변 본문을 유지한 채 대상 블록만 진행 상태로 표시한다.
- 과거 답변에는 기존 흐름 복원 경로를 유지한다. 모델·첨부 조건을 모두 복원할 수 없는 과거 데이터는 새 기본 조건을 조용히 적용하지 않는다.

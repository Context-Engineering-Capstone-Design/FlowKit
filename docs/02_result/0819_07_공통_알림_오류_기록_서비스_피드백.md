## 목표

모든 주요 작업의 성공·실패·부분 실패·진행 상태를 같은 규칙으로 표시한다. 서버 오류와 클라이언트 오류는 민감정보를 제거해 추적 가능하게 저장하고, 응답의 `traceId`와 로그를 연결한다. 사용자가 서비스 오류나 개선 의견을 제출하는 기능도 완성한다.

## 대상 기능

- BE-USERSET-007
- BE-NOTIFY-002~006
- FE-AUTH-003·007
- FE-USERSET-007
- FE-NOTIFY-001~005

BE-NOTIFY-001의 기본 오류 응답 형식은 이미 있다. 이번 마일스톤에서는 모든 예외와 화면이 그 형식을 일관되게 사용하도록 확장한다.

## 현재 상태와 문제

- `AppError`는 `errorCode`, `message`, `detail`, `traceId`를 반환한다.
- `traceId`는 응답마다 만들지만 서버 로그나 DB에 같은 값이 저장되지 않는다.
- 등록되지 않은 FastAPI·Pydantic·DB·일반 예외는 같은 형식이 아닐 수 있다.
- 정제 전체 승인만 성공·실패 목록을 나눠 반환한다.
- FE 오류 배너는 채팅 store 안에 있어 인증·설정·첨부 등 앱 전체 기능이 공유하기 어렵다.
- 공통 토스트, 요청 시간 초과 안내, 클라이언트 오류 수집, 서비스 피드백이 없다.

## 확정 구현 방식

### 응답 호환성

- 기존 성공 응답 본문을 전역 envelope로 감싸지 않는다.
- 주요 변경 API 응답에 선택 필드 `actionMeta`를 추가한다.
- 기존 FE가 사용하던 최상위 데이터 필드는 유지한다.
- 오류 응답은 기존 네 필드를 유지한다.

오류 응답:

```json
{
  "errorCode": "도메인_오류_코드",
  "message": "사용자용 안내",
  "detail": null,
  "traceId": "uuid"
}
```

성공 메타데이터:

```json
{
  "actionType": "api_key_saved",
  "successCode": "API_KEY_SAVED",
  "message": "API 키를 저장했습니다.",
  "affectedResourceId": "uuid"
}
```

### traceId 생성

- 요청 시작 시 middleware에서 `traceId`를 한 번 만든다.
- `request.state.trace_id`에 보관한다.
- 정상 응답 헤더 `X-Trace-Id`와 오류 응답 본문에 같은 값을 넣는다.
- 오류 로그도 같은 값을 기본 키로 사용한다.
- 클라이언트가 임의로 보낸 traceId를 서버 traceId로 신뢰하지 않는다.

### 로그 보안

저장하지 않는 값:

- Authorization 헤더와 access·refresh token
- 사용자 API 키 원문·암호문
- 첨부 파일 본문
- 전체 사용자 질문·AI 답변
- Python stack trace를 사용자 응답에 노출한 값

서버 stack trace는 운영 로그 접근 권한이 분리된 경우에만 내부 필드로 저장한다. DB 저장본에는 길이 제한과 마스킹을 적용한다.

### 부분 실패

공통 형식:

```json
{
  "processed": [{ "resourceId": "uuid" }],
  "failed": [
    {
      "resourceId": "uuid",
      "errorCode": "ITEM_NOT_FOUND",
      "message": "대상을 찾을 수 없습니다."
    }
  ],
  "actionMeta": {
    "actionType": "bulk_refine_approve",
    "successCode": "PARTIAL_SUCCESS",
    "message": "3개 중 2개를 처리했습니다."
  }
}
```

항목별 내부 예외 문자열을 그대로 반환하지 않는다.

## 데이터 구조

### `ErrorLog`

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| `trace_id` | UUID | 요청에서 생성, 고유값 |
| `user_id` | UUID 또는 null | 확인된 사용자만 기록 |
| `request_path` | 문자열 | query의 민감값 제외 |
| `method` | 문자열 | HTTP method |
| `error_code` | 문자열 | 표준 오류 코드 |
| `message` | 문자열 | 안전하게 줄인 내부 요약 |
| `exception_type` | 문자열 또는 null | 클래스 이름만 |
| `status_code` | 정수 | 응답 상태 |
| `created_at` | 시각 | 발생 시각 |

### `ClientErrorLog`

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| `id` | UUID | 기본 키 |
| `trace_id` | UUID | 서버 수신 요청 traceId |
| `user_id` | UUID 또는 null | 선택 인증 |
| `client_error_type` | 문자열 | 허용 목록 또는 길이 제한 |
| `message` | 문자열 | 마스킹·길이 제한 |
| `page_context` | JSON 또는 null | 경로·기능·resource ID 정도만 허용 |
| `user_agent` | 문자열 또는 null | 길이 제한 |
| `created_at` | 시각 | 수신 시각 |

### `ServiceFeedback`

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| `id` | UUID | 기본 키 |
| `user_id` | UUID | 작성 사용자 |
| `feedback_type` | enum | `error`, `usability`, `context`, `branch`, `other` |
| `content` | Text | 공백 제외 최소 1자, 최대 길이 제한 |
| `context_info` | JSON 또는 null | 현재 화면·채팅·브랜치 식별 정보 |
| `created_at` | 시각 | 제출 시각 |

오류 로그와 피드백은 사용자 삭제 정책과 보관 정책을 구현 전 확정한다.

## 오류 코드 체계

### 유지할 원칙

- 도메인별 접두사를 사용한다: `AUTH_`, `CHAT_`, `BRANCH_`, `MESSAGE_`, `REFINE_`, `CONTEXT_`, `AI_`, `API_KEY_`, `ATTACHMENT_`.
- 같은 원인에는 모든 API에서 같은 코드를 쓴다.
- Pydantic 422 응답도 표준 형식으로 바꾼다.
- 404와 403을 구분할 때 다른 사용자의 resource 존재 여부가 새지 않게 한다.
- 사용자용 문구와 운영용 상세를 분리한다.

### 예외 처리 대상

- `AppError`
- FastAPI 요청 검증 오류
- 인증 토큰 오류
- DB 무결성·연결 오류
- 모델 Provider 오류
- 파일 저장소 오류
- 처리되지 않은 일반 예외

처리되지 않은 예외는 `INTERNAL_ERROR`로 응답하고 반드시 ErrorLog를 남긴다.

## API 계약

### 서비스 피드백 제출

`POST /api/settings/feedback`

요청:

```json
{
  "feedbackType": "usability",
  "content": "개선 의견",
  "contextInfo": {
    "page": "workspace",
    "chatId": "uuid",
    "branchId": "uuid"
  }
}
```

응답:

- `feedbackId`
- `submittedAt`
- `actionMeta`

질문·답변 본문은 `contextInfo`에 받지 않는다.

### 클라이언트 오류 수집

`POST /api/client-errors`

- 로그인 사용자는 user ID를 연결한다.
- 로그인 전 오류도 받을 수 있도록 선택 인증을 사용한다.
- 요청 횟수 제한과 본문 길이 제한을 둔다.
- 수집 API 자체 실패는 다시 같은 API로 보고하지 않는다.
- 응답에는 `logId`, `receivedAt`만 반환한다.

## 프론트엔드 상태 설계

### `notificationStore`

채팅 기능에서 분리한 앱 공통 상태로 둔다.

```ts
interface NotificationState {
  banner: ErrorBannerState | null
  toast: ToastState | null
  showError(error: unknown): void
  dismissBanner(): void
  showToast(input: ToastInput): void
  clearToast(): void
}
```

규칙:

- 배너는 복구가 필요한 오류에 사용한다.
- 토스트는 성공·정보·주의 결과에 사용한다.
- 새 배너·토스트는 같은 종류의 이전 항목을 교체한다.
- 토스트는 일정 시간 뒤 사라지고 hover·키보드 포커스 중에는 시간을 멈춘다.
- API 키 미등록처럼 바로 할 수 있는 조치가 있으면 action 버튼을 제공한다.
- `detail`과 stack trace는 표시하지 않는다.

### 요청 진행 상태

- 기능별 `isLoading` 또는 resource별 pending 상태를 사용한다.
- 같은 요청 버튼만 비활성화한다.
- 공통 timeout helper로 일정 시간이 지나면 다시 시도 안내를 표시한다.
- 실제 HTTP 요청을 취소할 수 있으면 AbortSignal을 연결한다.
- 시간 초과 뒤 늦게 온 응답이 최신 상태를 덮지 않도록 request ID를 확인한다.

### 인증 만료

- 토큰 재발급 실패 시 token 저장소와 `authStore.user`를 함께 비운다.
- 로그인 화면으로 전환한 뒤 세션 만료 안내 배너를 표시한다.
- 재발급 처리 중 여러 요청이 실패해도 안내는 한 번만 표시한다.
- 로그인 성공 후 오래된 인증 오류 배너를 지운다.

## 서비스 피드백 화면

- 프로필 팝업의 `피드백 남기기`로 연다.
- 유형은 `오류`, `사용성 불편`, `Context 편집 문제`, `브랜치 기능 문제`, `기타` 중 하나만 선택한다.
- 내용은 빈 값과 최대 길이를 화면에서 먼저 검증한다.
- 현재 화면, chat ID, branch ID만 선택적으로 붙인다.
- 메시지 본문과 Context 본문은 자동 첨부하지 않는다.
- 제출 중 닫기와 중복 제출을 막는다.
- 실패 시 유형·내용을 유지한다.
- 성공 시 입력을 비우고 닫은 뒤 완료 토스트를 표시한다.

## 클라이언트 오류 수집 범위

자동 수집:

- React Error Boundary가 잡은 렌더링 오류
- 처리되지 않은 Promise 오류 중 제품 기능 오류
- 예상하지 못한 API 응답 형식

자동 수집하지 않는 항목:

- 사용자가 취소한 로그인·파일 선택
- 서버가 이미 정상적으로 반환한 검증 오류
- 네트워크 오프라인 반복 오류 전체
- 수집 API 자체 오류

전송 전 이메일, 토큰, API 키 형태, 긴 사용자 입력을 마스킹한다.

## 구현 결과

- 요청마다 `trace_id`를 만드는 middleware(`app/main.py`)를 추가했다. 정상 응답은 `X-Trace-Id` 헤더로, 오류 응답은 본문의 `traceId`로 같은 값을 돌려주고, `ErrorLog`에도 같은 값을 저장한다.
- `AppError`, Pydantic 검증 오류, 처리되지 않은 일반 예외를 같은 4개 필드(`errorCode`, `message`, `detail`, `traceId`) 형식으로 통일했다(`app/exceptions.py`). 처리되지 않은 예외는 `INTERNAL_ERROR`로 응답하며 `ErrorLog`에 예외 클래스 이름과 요청 경로를 남기고, Authorization 헤더·토큰·API 키·첨부 본문·대화 본문은 저장하지 않는다.
- `ErrorLog`, `ClientErrorLog`, `ServiceFeedback` 모델과 마이그레이션(`a81907observability`)을 추가했다. `POST /api/client-errors`(선택 인증, 요청 횟수 제한 20회/60초, 메시지 500자 제한)와 `POST /api/settings/feedback`을 연결했다.
- 정제 전체 승인·거절과 주요 mutation(정제 실행/승인/거절/정리, 인증·설정 API 등) 응답에 `actionMeta`(`actionType`, `successCode`, `message`, `affectedResourceId`)를 추가했다. 부분 실패는 `processed`/`failed` 목록으로 분리하고, 내부 예외 문자열 대신 안전한 오류 코드·문구만 반환한다.
- 프론트엔드에 `notificationStore`(전역 배너·토스트), `ErrorBanner.tsx`, `Toast.tsx`, `FeedbackModal.tsx`, `errorReporting.ts`(Error Boundary·전역 오류→클라이언트 오류 수집 연결), `requestTimeout.ts`(요청별 30초 제한, `AbortSignal` 연결, 최신 요청만 상태 반영)를 추가했다. 채팅·인증·설정의 지역 오류 상태를 공통 알림으로 옮겼다.
- 인증 만료 처리를 `authExpiration.ts`로 정리해, 토큰 재발급 실패 시 세션·화면 상태를 함께 비우고 안내를 한 번만 띄우도록 했다(`api/client.ts`의 `authExpirationNotified` 플래그).
- 서비스 피드백 화면은 유형(`오류`/`사용성 불편`/`Context 편집 문제`/`브랜치 기능 문제`/`기타`) 선택, 빈 값·최대 길이 화면 검증, 제출 중 중복 제출 방지, 성공 시 입력 비우고 닫기, 실패 시 입력 유지를 구현했다. 메시지·Context 본문은 자동으로 붙이지 않는다.

## 검증 결과

- 자동 테스트: `backend` pytest 157개(`test_notifications.py`, `test_observability.py`, `test_service_feedback.py` 포함), `frontend` vitest 21개(`notificationStore.test.ts`, `Toast.test.tsx`, `errorReporting.test.ts`, `requestTimeout.test.ts`, `FeedbackModal.test.tsx`, `chatStore.notifications.test.ts` 포함) 모두 통과. `npx tsc --noEmit`, `npm run lint`, `npm run build` 통과.
- 실제 브라우저 확인: 프로필 메뉴의 "피드백 남기기" → 유형 선택·내용 작성·제출까지 진행해 `service_feedbacks` 테이블에 올바른 유형(enum 값)과 내용으로 저장되는 것을 DB에서 직접 확인했다. 정제 요청이 클라이언트 제한 시간(30초)을 넘겼을 때 상단에 "요청 시간이 초과되었습니다" 배너와 "같은 지시로 다시 시도" 버튼이 뜨는 것, 다시 시도 시 같은 배너가 다시 뜨는 것(중복 배너 아님)을 확인했다. 강제로 500 오류를 만들어 `ErrorLog`에 같은 `traceId`로 기록되는 것도 백엔드에서 직접 재현해 확인했다.
- 브라우저로 직접 확인하지 못한 항목: React Error Boundary가 렌더링 오류를 잡아 클라이언트 오류로 전송하는 경로, 세션 만료 후 로그인 화면 전환과 단일 안내, API 키 미등록 배너에서 설정 모달로 이동, 첨부 업로드 관련 알림. 이 항목들은 자동 테스트로만 검증됐다.

## 남은 제한 사항

- **처리되지 않은 예외에서 CORS 헤더가 빠지는 문제를 발견했다.** `app.add_exception_handler(Exception, unexpected_error_handler)`로 등록한 핸들러는 FastAPI/Starlette 구조상 `ServerErrorMiddleware`(가장 바깥쪽)에서 실행되는데, 이 계층은 `CORSMiddleware`보다 바깥에 있어 그 핸들러가 만든 응답에는 CORS 헤더가 붙지 않는다. 브라우저에서는 실제 원인(500 오류)이 아니라 "CORS policy" 오류로만 보여 사용자가 상황을 알기 어렵다. 이번 검증 중 실제로 이 증상으로 나타난 500 오류(아래 enum 문제)는 고쳤지만, 이 미들웨어 순서 문제 자체는 고치지 않았다 — 앞으로 다른 원인으로 처리되지 않은 예외가 나면 같은 방식으로 CORS 오류처럼 보일 수 있다. 고치려면 CORS보다 안쪽에서 예외를 잡아 표준 오류 응답을 직접 반환하도록 미들웨어 순서를 바꿔야 하며, 별도 확인 후 진행이 필요하다.
- 이번 검증 중 이 마일스톤과 무관한 백엔드 버그(`AiResponseJob.job_type`/`status`, `Attachment.status`, `AiResponseFeedback.rating`, `ServiceFeedback.feedback_type` 등 enum 컬럼이 Postgres에 저장된 소문자 값 대신 SQLAlchemy 기본값인 대문자 이름을 보내 요청이 전부 실패하던 문제)를 발견해 별도 커밋(`30275e2`)으로 고쳤다. 위 CORS 문제 때문에 실제 화면에는 "서버에 연결하지 못했습니다"로만 보였다.
- "구현 전 확인할 결정" 중 오류 로그·피드백의 보관 기간과 탈퇴 시 삭제·익명화 정책은 이번에 구현하지 않았다(자동 삭제 Worker는 원래 범위 밖). 클라이언트 오류 수집 요청 제한(20회/60초)과 stack trace 비저장 정책은 구현했다.

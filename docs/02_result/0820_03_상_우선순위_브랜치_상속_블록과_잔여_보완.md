## 배경

두 조사 문서를 다시 살펴보니, 0819_09가 찾은 "중" 우선순위 8건은 이미 `docs/02_result/0819_11_중간_우선순위_기능명세_보완.md`(커밋 `01df99a`)로 전부 해결되어 있었다. 유일하게 코드가 아니라 사용자 판단만 남아 있던 BE-AIRESP-001(Context 적용 시 "결합"이냐 "대체"냐) 하나만 이번에 함께 정리한다.

남은 실제 구현 대상은 0820_01 조사의 상 2건·중 6건 중, 아래 두 가지를 뺀 7건이다.

- 요청 제한시간(FE-NOTIFY-005/AI-CORE-005), 재생성 시 검색 근거(AI-SEARCH-002 계열) 관련 항목은 `docs/01_plan/0820_02_기본_채팅_경험_보완과_모델_공급자_교체.md`에서 다른 세션이 다루고 있어 제외한다.

구현 착수 전 코드를 다시 확인해, 0820_01이 "확인 필요"로 남겨둔 것 외에 실제로 이미 고쳐진 항목이 없는지도 재검증했다(아래 "구현 전 재검증" 참고).

## 목표

1. 하위 브랜치가 이어받은 블록에 대한 평가·재생성·정제가 명세와 요구사항(REQ-019, NFR-007)에 맞게 동작하게 한다.
2. 메시지 전송 화면 흐름을 기본 채팅 수준으로 보완한다(전송 실패 시 입력 보존, 전송 직후 블록 표시).
3. Context 패널에서 바로 브랜치를 만들 수 있게 한다.
4. 로그아웃이 실제로 현재 세션의 인증 토큰을 무효화하게 한다.
5. 정제 결과 승인·거절이 이미 처리된 경우 화면을 최신 상태로 맞춘다.
6. BE-AIRESP-001 명세 문구를 실제 동작("대체")에 맞게 고친다.

## 사용자 확정 사항 (판단이 필요했던 항목)

- **이어받은 블록 답변 재생성**: 화면에서 재생성 버튼을 숨긴다. 하위 브랜치에 사본을 만들어 재생성하지 않는다.
- **이어받은 블록 정제**: 정제 대상 선택에서 제외한다. 사본을 만들어 반영하지 않는다.
- **요청 제한시간**: 0820_02가 이미 다루므로 이번 계획에서는 손대지 않는다.
- **BE-AIRESP-001 결합/대체**: 코드(대체)를 유지하고, BE기능명세서 문구를 코드에 맞게 고친다. (기획 문서 수정은 원칙적으로 하지 않지만, 이번 건은 사용자가 직접 승인했다.)

## 범위

### 마일스톤 A · 하위 브랜치가 이어받은 블록 처리 (상)

배경: `message_service.get_editable_block`은 블록이 `branch.id` 소유가 아니면(조상 브랜치에서 이어받았으면) `ValidationError`를 던진다. 평가(피드백) 조회·저장이 이 함수를 거쳐가서, 화면이 브랜치를 열 때마다 모든 AI 답변의 평가를 한꺼번에 조회하는 `refreshFeedbacks`가 하나라도 실패하면 전체가 실패로 처리된다. 그 결과 브랜치 생성·전환이 화면에서는 오류로 보인다.

- [x] **A1. 이어받은 답변 평가 허용**: `backend/app/services/ai_response_service.py`의 `_require_assistant_block`이 `message_service.get_editable_block` 대신 `get_visible_block`을 쓰도록 바꾼다. 평가는 내용을 바꾸지 않으므로 소유 검사가 필요 없다. `regenerate`(재생성)는 내용을 바꾸므로 `get_editable_block`을 그대로 쓴다.
- [x] **A2. 이어받은 답변은 재생성 버튼을 숨긴다**: 블록이 몇 번 브랜치 소유인지 화면이 알아야 한다.
  - `backend/app/schemas/chat.py`, `backend/app/schemas/message.py`의 블록 응답 스키마에 `branchId`를 추가하고, 채팅 상세·전송·재생성 응답 생성 지점에서 채워 넣는다.
  - `frontend/src/types/api.ts`의 `MessageBlock`, `BlockResponse`에 `branchId`를 추가한다.
  - `MessageBlockItem.tsx` → `MessageBlockActions.tsx`로 `isOwnBranch` 여부를 넘기고, 아니면 재생성 버튼을 렌더링하지 않는다.
- [x] **A3. 이어받은 블록은 정제 대상에서 제외한다**:
  - `backend/app/services/refine_service.py`의 `run_refine`에서, 선택된 블록 중 `block.branch_id != branch.id`인 것이 있으면 `ValidationError`로 거절한다.
  - `frontend/src/components/ContextPanel.tsx`의 `RefineForm`에서, 선택된 블록 중 이어받은 것이 있으면 "블록별로 정제하기" 버튼을 비활성화하고 안내 문구를 보여준다(A2에서 추가한 `branchId`로 판단).

**완료 기준**: 하위 브랜치에서 이어받은 AI 답변에 좋아요·싫어요를 누르면 저장된다. 그 답변의 재생성 버튼은 보이지 않는다. 이어받은 블록을 선택하면 정제 버튼이 비활성화되고 사유가 보인다. 브랜치를 만들거나 사이드바에서 하위 브랜치로 전환해도 오류 배너가 뜨지 않는다.

### 마일스톤 B · 메시지 전송 화면 흐름 (중)

- [x] **B1. 전송 직후 질문 블록 표시**: `chatStore.ts`의 `sendMessage`가 API 호출 전에 임시 사용자 블록을 `blocks`에 추가한다. 응답이 오면 실제 사용자·AI 블록으로 교체하고, 실패하면 임시 블록을 지운다. **범위 축소**: 계획과 달리 별도의 "생성 중" 임시 AI 블록은 만들지 않았다. 임시 질문 블록이 목록 맨 아래에 들어가면서 기존 "답변을 쓰는 중…" 한 줄 표시(`ChatArea.tsx`)가 자연히 그 바로 아래에 나타나 같은 효과를 낸다. 실제 AI 블록 컴포넌트를 흉내 내는 것보다 위험이 작다고 판단했다.
- [x] **B2. 저장 전 실패 시 입력 보존**: `sendMessage`의 catch에서, 서버 오류 상세(`detail`)가 없는 경우(질문이 아직 서버에 저장되지 않은 실패 — 첨부 문제, 지원하지 않는 모델, 연결 실패 등)에는 `openChat`을 호출하지 않는다. `detail`이 있는 경우(질문은 저장됐고 AI 응답만 실패)에만 기존처럼 `openChat`으로 화면을 다시 맞춘다.

**완료 기준**: 질문을 보내면 답을 기다리는 동안에도 방금 보낸 질문이 바로 보인다. 첨부 파일 문제 등으로 질문이 서버에 저장되기 전에 실패하면 입력 내용과 첨부가 그대로 남아 다시 보낼 수 있다.

**완료 기준**: 로그아웃한 뒤 같은 accessToken으로 `/api/auth/me`를 호출하면 401이 온다. 정상 로그인 상태에서는 기존과 동일하게 동작한다.

## 구현 결과

- 이어받은(조상 브랜치 소유) AI 답변의 평가 조회·저장은 `get_visible_block`으로 완화해 허용했다. 재생성·정제는 원본 대화를 바꾸므로 그대로 막되, 화면에서 재생성 버튼을 숨기고(`isOwnBranch`) 정제 대상 선택에서도 안내와 함께 막았다. 이로써 하위 브랜치를 만들거나 전환할 때 `refreshFeedbacks` 전체 실패로 오류 배너가 뜨던 문제가 해결된다.
- 메시지 전송은 임시 사용자 블록을 먼저 화면에 넣고, 성공하면 실제 블록으로, 실패하면 지운다. 질문이 서버에 저장되기 전 실패(`errorDetail`이 없는 경우)에는 화면을 다시 불러오지 않아 입력·첨부가 보존된다.
- Context 패널에 "이 Context로 브랜치 생성" 버튼을 추가했다.
- accessToken에 세션 id(`sid`)를 담아, 로그아웃·refreshToken 회전 시 그 자리에서 쓰던 토큰도 만료 전에 즉시 무효화되게 했다(요청마다 `AuthSession` 조회 1건이 추가된다).
- 정제 결과 승인·거절이 실패하면(예: 이미 처리된 결과) 정제 작업을 다시 조회해 화면을 서버 상태로 맞춘다.
- BE기능명세서 2.8의 "결합" 표현을 실제 동작(대체)에 맞게 고쳤다.

## 위험과 제한

- **브라우저 직접 확인을 하지 못했다.** 로컬 백엔드 개발 서버(포트 8000)가 `--reload` 없이 이번 작업 훨씬 전에 떠 있었고, 다른 세션이 같은 저장소에서 작업 중이라는 것이 확인되어 최신 코드를 반영하려고 재시작하지 않았다(재시작하면 그 세션의 검증이 끊길 수 있다). 그 결과 마일스톤 A(브랜치 상속 처리)·B(전송 화면 흐름)·C(브랜치 생성 버튼)는 자동 테스트로만 확인했다. 특히 A는 화면 여러 컴포넌트에 걸친 상태 흐름이라 자동 테스트가 커버하지 못하는 시각적 문제(레이아웃 깨짐 등)가 남아 있을 수 있다.
- **B1은 계획보다 범위를 줄였다.** "생성 중" 표시의 임시 AI 블록을 별도로 만들지 않고 기존 한 줄 표시를 재사용했다. 실제 AI 메시지 블록처럼 보이게 하려면 후속 작업이 필요하다.
- **D는 요청마다 DB 조회가 하나 늘어난다.** `AuthSession`을 매 요청 조회하므로, 트래픽이 커지면 캐싱 등 별도 최적화가 필요할 수 있다. 지금 규모에서는 문제가 되지 않는다.
- 이번 작업 중 `frontend/src/components/MessageBlockItem.tsx`와 그 테스트 파일에 다른 세션의 변경(표 안 `<br>` 처리, 스크립트 제거를 위한 `rehypeRaw`/`rehypeSanitize` 도입)이 섞여 있어, 그 부분만 임시로 떼어내고 이번 커밋을 만든 뒤 다시 원래대로 복원했다. 이번 커밋(`124cbad`)에는 그 변경이 포함되지 않았으며, 해당 세션이 별도로 커밋해야 한다.

# 0821_10 인용 스니펫 위치 저장과 맥락 전달

## 배경

드래그로 메시지 일부를 골라 "채팅에 추가"로 인용하면([0820_13](../02_result/0820_13_드래그_범위_Context_선택.md)), 그 스니펫 문자열만 AI에 넘어간다. 이 상태에서 문제가 확인됐다.

메시지 안에 같은 문구("K")가 여러 번 나오는 상황에서, 사용자가 특정 위치의 "K"를 골라 질문했더니 AI가 "K는 별도의 설명 없이 단독으로 적힌 문자로, 무엇을 뜻하는지 알 수 없다"고 답했다. 원인을 확인해보니 두 가지가 겹쳐 있었다.

1. **위치 계산이 부정확하다** — `captureSelection`([textRangeSelection.ts:48](../../frontend/src/lib/textRangeSelection.ts))이 실제 드래그 지점이 아니라 `flatText.indexOf(text)`로 위치를 다시 찾는다. 같은 문구가 메시지 앞쪽에 또 있으면 항상 그 앞쪽 위치로 잘못 잡힌다. 0820_13 결과 문서에도 이미 알려진 제한으로 남아 있다.
2. **AI에 스니펫만 통째로 전달되고 주변 맥락은 아예 빠진다** — `context_service.build_range_snapshot`이 스니펫 원문 자체를 `ContextItem.content`로 넘기고(주변 문장 없음), `modeling/prompts/answer.py`의 `CONTEXT_BLOCK`은 "오직 이 내용만 근거로 답하라"고 지시한다. 그래서 애매한 한두 글자만 골랐을 때 AI는 그 글자가 원문 어디서 어떤 맥락으로 쓰였는지 알 방법이 없다.

여기에 더해, 위치 정보 자체가 저장되지 않아서 채팅 내역에 남은 인용 태그를 나중에 다시 봐도 "이게 원문 어디를 가리켰는지" 확인할 방법이 없다([0821_02](../02_result/0821_02_전송된_Context_스니펫_대화내_영구_표시.md) 결과 문서의 남은 제한 사항).

## 목표

- 드래그로 고른 위치를 실제 선택 지점 기준으로 정확히 계산하고, 버전 단위로 서버에 저장한다.
- AI에 스니펫을 넘길 때 이 위치를 기준으로 앞뒤 맥락을 함께 보내, 애매한 한두 글자만 골라도 정확히 답할 수 있게 한다.
- 채팅 내역에 남은 인용 태그를 클릭하면, 원문에서 그 위치를 다시 하이라이트해 보여준다.

## 설계 결정 (초안, 진행 전 확인 필요)

- **맥락 범위는 고정 글자 수로 정한다** — 스니펫 앞뒤로 각 100자, 블록 경계를 넘지 않는다. 문장 단위로 자르는 방식은 한국어 문장 경계 판별이 별도 작업이라 이번 범위에서 뺀다.
- **선택 지점 표시는 대괄호로 감싼다** — 예: `...가방 안에는 A, B, K 세 글자가 적혀 있었다. 그중 [[K]]는 승객이...`. 프롬프트에 "대괄호로 표시된 부분이 사용자가 실제로 지정한 지점, 나머지는 이해를 돕는 주변 맥락"이라고 안내를 추가한다.

## 범위

### 백엔드

1. `AppliedContextItem`(`backend/app/models/context.py`)에 `start_offset`·`end_offset`(nullable Integer) 컬럼을 추가하는 Alembic 마이그레이션을 만든다. 블록 전체를 고르는 기존 방식(오프셋 없음)은 NULL로 둔다.
2. `ContextRangeIn`(`backend/app/schemas/conversation.py`)에 `startOffset`·`endOffset`을 추가한다.
3. `context_service.ContextRangeSpec`·`build_range_snapshot`이 오프셋을 받아 `version.content[start_offset:end_offset] == snippet_text`인지 검증한다(현재는 단순 부분 문자열 포함 여부만 확인해 위치를 확정하지 않는다 — 이 검증으로 위조 스니펫도 계속 막는다).
4. `context_service.save_log`가 오프셋을 `AppliedContextItem`에 함께 저장한다.
5. `AppliedContextOut`(`backend/app/schemas/conversation.py`)과 `MessageBlockOut`의 인용 목록(`backend/app/schemas/chat.py`)에 `startOffset`·`endOffset`을 추가해, 전송 응답과 채팅 재조회 양쪽에서 프론트가 위치를 받게 한다.
6. AI 입력을 만드는 단계에서 오프셋을 이용해 스니펫 앞뒤 맥락(각 100자, 블록 경계 안)을 잘라 붙이고, 선택 지점을 `[[ ]]`로 표시한 문자열을 `ContextItem.content`로 만든다.
7. `modeling/prompts/answer.py`의 `CONTEXT_BLOCK`에 대괄호 표시 안내 문구를 추가한다.

### 프론트엔드

1. `captureSelection`(`frontend/src/lib/textRangeSelection.ts`)이 `flatText.indexOf(text)` 대신, 실제 드래그한 `Range`의 시작·끝 지점까지 DOM을 순회해 문자 수를 세는 방식으로 위치를 계산하도록 바꾼다 — 같은 문구가 앞쪽에 또 있어도 실제 선택 위치를 정확히 잡는다.
2. `sendMessage`·`editBlock`이 서버로 보내는 `ContextRangeIn`(`chatStore.ts`)에 `startOffset`·`endOffset`을 함께 담는다.
3. 서버 응답에 담겨 오는 오프셋을 `MessageBlock.appliedContext` 타입(`types/api.ts`)에 추가한다.
4. 채팅 내역의 인용 태그(`MessageBlockItem.tsx`의 `AppliedContextTagList`)를 클릭하면, 그 오프셋이 가리키는 원본 블록·버전의 렌더링된 본문에서 해당 구간을 하이라이트한다 — 기존 입력창 태그 호버 미리보기가 쓰는 하이라이트 경로(`rehypeHighlightRanges.ts`)를 재사용한다.
5. 하이라이트 대상 블록이 현재 화면 밖에 있으면 그 위치로 스크롤한 뒤 하이라이트한다.

### 범위에서 뺀 것

- 사이드 채팅으로 가져온 블록은 인용 목록 자체가 채워지지 않는 기존 제한(0821_02)이 남아 있다. 이번 작업에서 이 경로는 고치지 않는다.
- 블록 전체를 고르는 기존 체크박스 방식은 오프셋 없이 그대로 둔다. 이번 위치 저장·맥락 전달은 드래그 범위 선택에만 적용한다.

## 완료 기준

- [x] 같은 문구가 메시지 안에 여러 번 나와도, 실제로 드래그한 위치가 정확히 저장된다.
- [x] 한두 글자만 골라 질문해도 AI가 스니펫 앞뒤 맥락을 함께 받아 정확히 답한다.
- [x] AI에게 전달되는 맥락 안에서 사용자가 실제로 고른 지점과 주변 맥락이 구분되어, 모델이 범위를 헷갈리지 않는다.
- [x] 채팅 내역의 인용 태그를 클릭하면 원문에서 그 위치가 하이라이트된다.
- [x] 위조된 오프셋(원문과 실제로 다른 위치)은 백엔드에서 거부된다.
- [x] 새로고침 후에도 위치 정보가 유지된다(버전 기준 저장이라 원문이 나중에 수정돼도 어긋나지 않는다).

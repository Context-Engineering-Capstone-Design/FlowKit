# 채팅 목록 중복 새로고침 정리

## 배경 (지금 무엇이 문제인가)

배포 서버에서 빈 "새 대화" 탭에 메시지를 하나 보냈을 때(AI 응답은 실패로 끝난 경우 포함), 좌측 사이드바의 "최근 대화" 목록이 몇 초 사이 여러 번 다시 그려지면서 항목이 순간적으로 늘었다 줄거나 순서가 바뀌는 것처럼 보였다.

## 원인 (코드상 왜 이렇게 되어 있는가)

메시지 하나를 보내고 응답이 끝나기까지, 서로 조율되지 않은 여러 곳에서 각각 채팅 목록을 다시 불러온다([loadChats](../../frontend/src/store/chatStore.ts)).

1. 새 대화가 만들어질 때 — 서버가 실시간 채널로 `chats_changed`를 보낸다([chat_service.py:66](../../backend/app/services/chat_service.py)). 같은 창이 이 신호를 받아 [handleRealtimeChatsChanged (chatStore.ts:1709)](../../frontend/src/store/chatStore.ts)에서 다시 불러온다.
2. 같은 순간, [ensureChat 내부(chatStore.ts:1926)](../../frontend/src/store/chatStore.ts)에서도 새 대화가 만들어지자마자 직접 한 번 더 불러온다.
3. 메시지 전송 응답에 제목이 새로 생겼으면 [sendMessage (chatStore.ts:991)](../../frontend/src/store/chatStore.ts)에서 또 한 번 불러온다.
4. AI 응답이 끝나면(성공이든 실패든) 서버가 다시 `chats_changed`를 보낸다([ai_response_service.py:358](../../backend/app/services/ai_response_service.py)). 같은 창이 이 신호로 또 한 번 불러온다.
5. 같은 시점에 [attachToJob의 onDone (chatStore.ts:1096)](../../frontend/src/store/chatStore.ts)에서도 직접 한 번 더 불러온다.

즉 메시지 한 번 보내고 응답 하나 받는 사이, 최대 다섯 번까지 겹쳐서 같은 목록을 다시 요청한다. 각 요청은 [loadChats](../../frontend/src/store/chatStore.ts)의 `latestChatListRequestId` 가드 덕분에 결과 자체가 뒤죽박죽 섞이지는 않지만(가장 나중에 시작한 요청의 결과만 반영됨), 그 사이 화면이 여러 번 다시 그려지는 건 막지 못한다. 이게 사이드바가 짧게 여러 번 깜빡이는 원인이다. 부수적으로 배포된 백엔드(Render 무료 플랜)에도 불필요한 요청이 반복해서 들어간다.

## 목표

같은 창에서 짧은 시간 안에 여러 신호(실시간 이벤트·전송 완료·새 대화 생성 등)가 겹쳐 오면, 채팅 목록 새로고침을 한 번으로 합친다. 최종적으로 목록이 최신 상태를 반영하는 결과는 그대로 유지한다.

## 범위

1. 신호에 의해 자동으로 일어나는 채팅 목록 새로고침 호출 지점을 하나의 공용 함수로 모은다. 여러 호출이 짧은 시간(수백 ms) 안에 겹치면 실제 네트워크 요청은 한 번만 나가도록 합친다.
2. 아래 호출 지점을 모두 이 공용 함수를 쓰도록 바꾼다.
   - [chatStore.ts:1926](../../frontend/src/store/chatStore.ts) (`ensureChat`, 새 대화 생성 직후)
   - [chatStore.ts:991](../../frontend/src/store/chatStore.ts) (`sendMessage`, 제목 생성 시)
   - [chatStore.ts:1096](../../frontend/src/store/chatStore.ts) (`attachToJob`, 응답 완료 시)
   - [chatStore.ts:1711](../../frontend/src/store/chatStore.ts) (`handleRealtimeChatsChanged`, 실시간 이벤트 수신 시 — 재연결 직후 강제 호출 포함)
   - [chatStore.ts:509](../../frontend/src/store/chatStore.ts) (`newChat`, 프로젝트 안에서 새 대화 생성 시)
   - [chatStore.ts:1047](../../frontend/src/store/chatStore.ts) (`retryAiResponseJob`, 재시도 직후)
3. 사용자가 직접 목록을 검색하거나(검색어 입력), 처음 화면을 열 때, 더 불러오기를 누를 때 등 사용자가 직접 일으키는 호출은 그대로 즉시 실행되도록 손대지 않는다.
4. 60초 간격의 안전망 폴링([chatStore.ts:82](../../frontend/src/store/chatStore.ts))은 애초에 겹칠 일이 드물어 범위에서 제외한다.

## 구현 결과 (2026-08-22)

기준 커밋: `2fe9c9b`

### 구현 항목

- [chatStore.ts](../../frontend/src/store/chatStore.ts)에 `scheduleChatsRefresh(get)` 공용 함수를 추가했다. 짧은 시간(300ms) 안에 여러 번 불려도 타이머 하나만 걸어두고, 그 시간이 지난 뒤 채팅 목록을 한 번만 다시 불러온다.
- 계획에 나열한 6곳(`ensureChat`, `newChat`, `sendMessage`, `retryAiResponseJob`, `attachToJob`의 `onDone`, `handleRealtimeChatsChanged`)을 모두 `loadChats()` 직접 호출 대신 `scheduleChatsRefresh(get)`을 쓰도록 바꿨다. 재연결 직후 강제 호출([chatStore.ts](../../frontend/src/store/chatStore.ts) `runRealtimeLoop`)은 `handleRealtimeChatsChanged`를 통해 자동으로 같이 반영된다.
- 사용자가 직접 검색어를 입력하거나 목록을 더 불러올 때 쓰는 `loadChats`·`loadMoreChats` 자체와 60초 안전망 폴링은 계획대로 손대지 않았다.

## 남은 제한사항 (미검증·범위 밖)

- 응답 완료 시점에는 `GET /api/chats?limit=10`이 여전히 두 번 나가는 경우를 관찰했다. 원인을 추적한 결과, 이번 계획의 대상인 "목록 새로고침 중복 호출"과는 다른 별도 문제로 보인다 — AI 응답이 끝난 직후 실시간 채널로 받은 대화 상세를 다시 반영하는 과정([handleRealtimeChatActivity](../../frontend/src/store/chatStore.ts))이 이미 끝난 작업을 다시 진행 중으로 착각해 같은 작업의 스트림에 한 번 더 붙는 것으로 보이며(`ai-response-jobs/.../stream` 요청이 두 번 나감), 그 과정에서 메시지 블록이 화면에 순간적으로 중복 렌더링되는 현상(`React` "same key" 경고, 실제 서버 데이터는 중복 없음)도 함께 확인했다. 이번 작업 범위 밖이라 손대지 않았고, 별도 조사·수정이 필요하다.

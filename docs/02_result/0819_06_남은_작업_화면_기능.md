## 화면 상태 설계

### 브랜치 생성 초깃값

`BranchModal`을 단순 열림 여부가 아니라 다음 초깃값과 함께 연다.

```ts
interface BranchDraft {
  baseBlockId: string
  contextBlockIds: string[]
  editedContent?: string
  sourceMode: 'header' | 'block' | 'edited-block'
}
```

- 헤더 버튼: 마지막 블록을 분기 지점으로 사용
- 블록의 `여기서 브랜치 생성`: 해당 블록을 분기 지점으로 사용
- 수정 중 `브랜치로 저장`: 해당 블록과 수정 내용을 사용

수정본 기반 브랜치는 원본 블록을 먼저 수정하지 않는다. 브랜치 생성 서비스가 새 브랜치에 수정본 버전을 만들도록 요청 계약을 확장한다.

### 메시지 편집 상태

블록별로 다음 값을 가진다.

- 편집 중인 블록 ID
- 원래 본문
- 입력 중 본문
- 저장 중 여부
- 영역 내 오류

한 번에 한 블록만 편집한다. 다른 블록 편집, 채팅·브랜치 전환, 모달 열기 전에는 현재 입력을 버릴지 확인한다.

### Context 편집 지시

- 지시문은 `ContextPanel` 지역 상태가 아니라 `chatStore`에 둔다.
- 같은 채팅·브랜치에서 패널만 닫고 열면 유지한다.
- 채팅·브랜치를 바꾸거나 새 채팅을 만들면 비운다.
- 최대 길이는 백엔드 `MAX_INSTRUCTION_LENGTH`와 같은 2,000자로 맞춘다.
- 빠른 지시를 누르면 값을 채운 뒤 입력창에 포커스를 옮긴다.

### Context 이름

- 편집 지시가 있으면 앞뒤 공백을 없애고 짧게 줄인 표시명을 사용한다.
- 지시가 없으면 `선택한 Context`를 기본 이름으로 쓴다.
- 표시명은 화면 상태이며 서버에 저장하지 않는다.

## 세부 기능

### 최근 대화 목록과 검색

- `nextCursor`가 있으면 목록 끝 근처에서 다음 페이지를 요청한다.
- 첫 페이지 요청과 추가 페이지 요청 상태를 분리한다.
- 같은 cursor의 중복 요청을 막는다.
- 새 검색어가 들어오면 기존 cursor와 목록을 초기화한다.
- 전체 목록 없음과 검색 결과 없음을 다른 문구로 표시한다.
- 요청 실패는 사이드바 목록 영역에 다시 시도 버튼을 표시한다.
- 접근 권한 오류로 대화 열기가 실패하면 해당 항목을 목록에서 제거한다.

### 브랜치 전환과 원본 위치

- 전환 성공 후 메시지 영역을 맨 위로 올린다.
- 선택 블록, 적용 Context, 정제 작업, 편집 초안을 초기화한다.
- 버릴 편집 내용이 있으면 전환 전에 확인한다.
- 원본 위치 이동은 다른 브랜치 전환 완료 후 DOM 렌더링을 기다려 스크롤한다.
- 원본 블록이 없으면 전역 오류가 아니라 Context 배너 안에 안내한다.
- 브랜치 생성 서버 오류는 모달 안에 표시하고 입력값을 유지한다.

### 메시지 블록 동작 메뉴

공통 동작:

- 복사
- 수정
- Context 편집
- 여기서 브랜치 생성

AI 블록 추가 동작:

- 좋아요·싫어요
- 답변 재생성

버전이 여러 개인 블록:

- 이전·다음 버전

버튼이 과도하게 늘어나지 않도록 자주 쓰는 동작과 더보기 메뉴를 나눈다. 키보드 포커스와 `aria-label`을 제공한다.

### 메시지 복사

- 활성 버전 본문을 서식 없는 텍스트로 복사한다.
- 성공·실패 알림 이벤트를 발행한다.
- Clipboard API가 없거나 거절되면 실패 상태를 표시한다.

### 메시지 수정

- 본문을 textarea로 바꾸고 현재 활성 버전 내용을 채운다.
- 취소, 브랜치로 저장, 저장 버튼을 표시한다.
- 저장은 기존 `editBlock` API를 사용해 새 버전을 만들고 활성화한다.
- 성공 뒤 버전 목록을 다시 읽고 편집 모드를 닫는다.
- 실패하면 입력값과 편집 모드를 유지한다.

### 수정본 기반 브랜치 생성

기존 브랜치 생성 요청에 선택 필드를 추가한다.

```json
{
  "editedBaseContent": "수정 중인 내용"
}
```

- 값이 있으면 새 브랜치의 분기 기준 블록에 사용자 수정 버전을 추가한다.
- 원본 브랜치 블록은 바꾸지 않는다.
- 백엔드는 해당 블록이 실제 분기 지점인지 다시 확인한다.
- 새 브랜치 생성과 수정 버전 저장은 한 트랜잭션으로 처리한다.

### Context 패널

- 최소·최대 너비 안에서 드래그로 조절한다.
- 너비는 브라우저 세션 동안 유지한다.
- 좁은 화면에서는 고정 패널 대신 오버레이로 표시하고 너비 조절을 감춘다.
- 블록 동작 메뉴에서 Context 편집을 누르면 블록 선택, 패널 열기, 입력창 포커스를 순서대로 수행한다.

### 정제 결과

- 요청 중 미리보기 영역에 진행 상태를 표시한다.
- 실패 시 입력 지시와 선택 블록을 유지하고 다시 시도 버튼을 제공한다.
- 결과 카드에 역할, 상태, 원본·정제 미리보기, 원본 위치 버튼을 표시한다.
- 결과를 받으면 첫 대상 블록으로 이동한다.
- 전체 거절은 기존 백엔드 `reject-all` API를 연결한다.
- 전체 승인·거절 부분 실패는 성공 항목만 갱신하고 실패 항목은 대기 상태로 남긴다.

### Context 적용·해제

- 적용 후 입력창으로 포커스를 옮긴다.
- 적용 이름과 블록 개수를 입력창 위에 표시한다.
- 적용·해제 성공 알림 이벤트를 발행한다.
- 해제해도 선택 블록은 유지한다.
- 메시지 전송 성공 후 적용 Context와 선택 블록을 함께 비운다.

- 블록 삭제와 순서 변경
- 여러 블록 동시 직접 수정
- 브랜치 병합
- 편집 초안의 서버 저장
- 공통 토스트 디자인과 오류 로그 수집은 마일스톤 5에서 처리

## 주의사항

- 현재 `MessageBlockItem`은 정제·평가·재생성·버전 이동을 함께 담당한다. 새 기능을 그대로 더하지 말고 동작 메뉴와 편집 폼을 분리한다.
- 브랜치 전환은 여러 상태를 비운다. 새 상태를 추가할 때 초기화 목록에서 빠뜨리지 않는다.
- DOM 이동은 브랜치 데이터 갱신 직후가 아니라 새 블록 렌더링 뒤 실행한다.

## 구현 결과

- 메시지 블록의 동작 메뉴와 편집 폼을 `MessageBlockActions.tsx`, `MessageEditForm.tsx`로 분리했다. `MessageBlockItem.tsx`는 두 컴포넌트를 조립하는 역할만 남았다.
- `useInfiniteChatList.ts` 훅으로 최근 대화 목록의 cursor 추가 로딩, 첫 페이지·추가 페이지 상태 분리, 같은 cursor 중복 요청 방지, 검색어 변경 시 초기화를 구현했다.
- `ConfirmDialog.tsx`로 편집 중 이탈 확인을 공통화하고, 채팅·브랜치 전환·모달 열기 전에 미저장 편집이 있으면 확인하도록 연결했다.
- `chatStore.ts`에 `BranchDraft`(`baseBlockId`, `contextBlockIds`, `editedContent`, `sourceMode`)를 두어 헤더·블록·수정 중 저장 세 진입 경로의 분기 지점을 구분한다.
- 수정본 기반 브랜치 생성을 위해 `editedBaseContent` 선택 필드를 백엔드에 추가했다(`schemas/chat.py`, `services/branch_service.py`, `routers/chat.py`). 원본 블록은 바꾸지 않고 새 브랜치에만 수정 버전을 만들며, 분기 지점이 아닌 블록을 지정하면 거절하고, 생성 실패 시 수정 버전도 남지 않는다 — `test_edited_branch_keeps_original_block_unchanged`, `test_edited_branch_rejects_block_that_is_not_a_branch_point`, `test_edited_branch_rolls_back_copy_when_creation_fails`로 검증했다.
- Context 패널에 드래그 크기 조절 핸들을 추가하고, 편집 지시문을 패널 지역 상태 대신 `chatStore`로 옮겨 패널을 닫았다 열어도 유지되게 했다. 블록 동작 메뉴의 "Context 편집 시작"은 블록 선택 → 패널 열기 → 입력창 포커스 순서로 동작한다.
- 정제 결과에 원본 위치 이동, 실패 후 같은 지시로 다시 시도, 전체 거절(`reject-all`) 연결, 전체 승인·거절의 부분 실패를 성공 항목만 갱신하고 실패 항목은 배너에 사유별로 표시하도록 구현했다.
- Context 적용 후 입력창 포커스 이동과 적용 이름·블록 개수 표시, 해제 후 선택 유지, 메시지 전송 성공 후 적용 Context·선택 블록 동시 초기화를 구현했다.

## 검증 결과

- 자동 테스트: `backend` pytest 157개, `frontend` vitest 21개 모두 통과. `npx tsc --noEmit`, `npm run lint`(oxlint), `npm run build` 모두 통과.
- 실제 브라우저 확인(Postgres·Gemini API 연동, 로컬 개발 로그인 사용): 로그인 → 채팅 진입, 메시지 블록의 복사·좋아요·수정 폼 열기/취소, "Context 편집 시작" 클릭 시 블록 선택·패널 열기·입력창 포커스가 순서대로 일어나는 것, 빠른 편집 칩 클릭 시 지시문이 채워지고 포커스가 유지되는 것, 블록별 정제 실행과 실패 후 "같은 지시로 다시 시도" 버튼 동작, 특정 블록에서 "여기서 브랜치 생성"을 눌렀을 때 분기 지점이 해당 블록으로 정확히 설정되고 새 브랜치로 전환 후 그 지점까지만 표시되는 것을 확인했다. 이 과정에서 콘솔 오류는 없었다.
- 브라우저로 직접 확인하지 못한 항목: 긴 대화 목록의 다음 페이지 자동 로딩과 검색 결과 없음/전체 없음/재시도 문구 구분, 여러 버전 블록의 이전·다음 이동, 수정 중인 내용으로 브랜치 저장(`sourceMode: 'edited-block'`) 시나리오, Context 패널 너비 드래그와 좁은 화면 오버레이, 다른 브랜치의 원본 Context 위치 이동, 파일 첨부·웹 검색 토글과 함께 쓰는 조합. 이 항목들은 자동 테스트(단위·컴포넌트 테스트)로만 검증됐다.

## 남은 제한 사항

- 위 "브라우저로 직접 확인하지 못한 항목"은 자동 테스트 통과만 확인했고, 실제 화면 조작으로는 검증하지 않았다.
- 이번 검증 중 이 마일스톤과 무관한 백엔드 버그(`AiResponseJob`·`Attachment`·`AiResponseFeedback` 등 enum 컬럼이 Postgres에 저장된 값과 다른 값을 보내 메시지 전송 자체가 실패하던 문제)를 발견해 별도 커밋(`30275e2`)으로 고쳤다. SQLite 기반 자동 테스트는 이 불일치를 잡아내지 못하며, 실제 Postgres로 메시지를 보내야 드러난다.
- Gemini 응답이 41초 이상 걸리는 경우가 있어, 프론트엔드 기본 요청 제한 시간(30초)보다 오래 걸리면 "요청 시간이 초과되었습니다" 안내와 함께 재시도가 필요하다. 재시도 자체는 정상 동작하지만, 이 환경의 네트워크 지연이 실제 운영 환경과 같은지는 확인하지 않았다.

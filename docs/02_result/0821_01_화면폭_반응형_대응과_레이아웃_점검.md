- 상태: 구현 완료 (마일스톤 A~D, E는 사용자 확인 대기)

## 기획 문서와의 관계

`기획 문서/` 전체를 확인한 결과 반응형·모바일·태블릿·화면폭·해상도에 관한 항목이 없다. FE 명세의 NFR-001·002도 "3단 작업 화면"과 "선택 블록 강조"만 정할 뿐 화면 크기를 전제하지 않는다. 즉 지금까지는 데스크톱 화면만 놓고 만들어졌고, 이번 작업은 기존 명세를 고치는 게 아니라 **새 요구 영역을 추가**하는 것이다.

이 문서는 계획 단계이므로 새 요구사항 번호(REQ-072, NFR-018)를 잠정적으로 붙여 두되, `기획 문서/`의 요구사항정의서·FE기능명세서에 실제로 반영할지는 사용자 결정을 먼저 받는다. 구현 전에 반영 여부를 확인한다.

## 배경

지금 화면은 좌측 사이드바(고정 236px, 마우스 hover로 펼침) + 중앙 채팅 + 우측 Context 패널(고정폭, 넓은 화면에서만 반응형 처리) 3단 구조다. 코드로 확인한 실제 상태는 아래와 같다.

- Tailwind 반응형 접두사(`sm:`, `md:`, `lg:`, `xl:`)가 전체 코드베이스에서 5곳(`lg:`만)만 쓰인다. 그중 4곳이 Context 패널 하나에 몰려 있다.
- 좌측 사이드바는 펼침·접힘이 `onPointerEnter`(마우스 진입) 기준이다. 터치 기기에는 마우스 진입이라는 개념이 없어 사이드바를 열 방법이 없다.
- 모달·팝오버 다수가 화면 크기와 무관한 고정 픽셀 폭이다(`w-[380px]`, `w-[480px]`, `w-56`, `w-64`, `w-72` 등). 좁은 화면에서는 화면 밖으로 밀려나거나 잘릴 수 있다.
- 답변 아래 근거 목록·메시지 목차·모델 선택 등 여러 상호작용이 `group-hover`로만 열린다. 마우스가 없는 기기에서는 그 기능 자체를 쓸 수 없다.
- 마크다운 표에 가로 스크롤 래퍼가 없다. 코드 블록은 있는데 표만 빠져 있다.
- 입력창 도구줄에 버튼 4개가 한 줄로 나열돼 있어, 좁은 화면에서 겹치거나 넘칠 가능성이 있다.

즉 지금 상태로 좁은 화면에서 열면 "레이아웃이 조금 어색한" 수준이 아니라, **사이드바를 열 수 없고 일부 팝오버 기능은 아예 쓸 수 없는** 수준이다.

## 목표

1. 모바일·태블릿을 포함한 다양한 화면폭에서 핵심 기능(대화 보기·전송, 사이드바 이동, Context 편집, 브랜치·사이드채팅 탐색)을 쓸 수 있게 한다.
2. 현재 화면 전체를 화면폭 구간별로 훑어, 깨지거나 잘리거나 겹치는 지점을 찾아 고친다.

## 마일스톤 A · 기준 정의

- [x] A1. 대응할 화면폭 구간을 정한다 — 계획한 3단(모바일/태블릿/데스크톱) 대신, 기존 코드에 이미 있던 유일한 기준점인 `lg`(1024px) 하나로 **좁음/넓음 2단**만 나눴다. 태블릿을 모바일과 같은 '좁음'으로 묶은 이유는 아래 A2에 적는다
- [x] A2. 구간별 규칙을 정한다 — **좁음(1024px 미만, 모바일+태블릿)**: 사이드바·Context 패널 모두 전체 화면 오버레이, 한 번에 하나만. **넓음(1024px 이상)**: 기존 3단 그대로. 계획에 있던 '태블릿은 사이드바 접힘 + 메인 + Context 2단'은 적용하지 않았다 — `md`(768px) 같은 새 기준을 하나 더 들이면 사이드바·Context 패널 두 곳의 오버레이 조건이 서로 다른 폭에서 바뀌어 검증 대상이 두 배로 늘고, 이미 코드에 있는 `lg` 기준과도 어긋난다. 좁음 구간 전체를 오버레이로 묶는 더 단순하고 위험이 적은 쪽을 택했다
- [x] A3. 점검 폭 — 375px(모바일), 768px(태블릿), 1280px(데스크톱) 세 값을 실제 기기 대신 브라우저 뷰포트 크기로 썼다
- [x] A4. 터치 기기(hover 불가)에서는 hover로만 드러나던 조작 버튼을 항상 노출하는 쪽으로 정했다

**완료 기준**: 구간 3개와 각 구간의 레이아웃 규칙, 점검 기기 목록이 문서에 남는다.

## 마일스톤 B · 레이아웃 골격 대응

- [x] B1. 사이드바가 접혀 있으면 항상 눌러서 열 수 있는 버튼을 중앙 채팅 헤더에 새로 뒀다. hover 미리보기(peek)는 `lg` 이상에서만 보조로 남긴다. **이번 조사로 드러난 사실**: 이 버튼은 좁은 화면뿐 아니라 넓은 화면에서도 원래 없었다 — 사이드바를 접으면 화면 가장자리 3px짜리 hover 영역이 유일한 재진입 경로였다. 마우스 사용자도 사실상 막혀 있던 기존 버그였다
- [x] B2. `lg` 미만에서 두 패널 모두 반투명 배경(backdrop)을 깔고, 배경을 누르면 닫히게 했다
- [x] B3. `lg` 미만에서는 한쪽을 열면 다른 쪽을 자동으로 닫아, 두 오버레이가 겹치는 경우 자체가 생기지 않게 했다
- [x] B4. 확인만 하고 수정하지 않았다 — 이미 `overflow-x-auto`로 가로 스크롤 처리가 돼 있어 좁은 화면에서도 각 탭이 눌리지 않게 찌그러지지 않는다
- [ ] B5. 적용하지 않았다 — A2에서 적은 이유로 태블릿을 별도 2단 구간으로 나누지 않고 모바일과 같은 오버레이 방식으로 묶었다. 태블릿에서 사이드바를 계속 펼쳐 둔 채 메인+Context를 보고 싶다는 요구가 확인되면 별도로 다룰 항목이다

**완료 기준**: 모바일 폭에서 사이드바와 Context 패널을 손가락 조작만으로 열고 닫을 수 있다. 두 패널이 동시에 화면을 가려도 조작 흐름이 끊기지 않는다.

## 마일스톤 C · 고정 폭 요소 대응

- [x] C1. 로그인 화면과 브랜치 생성 모달의 고정 폭(`w-[380px]`, `w-[480px]`)을 `w-full max-w-[...]`로 바꿨다. API 키·프로필·피드백 모달은 조사 결과 이미 같은 패턴(`w-full max-w-[...]`)이라 손대지 않았다. Project 관리 모달은 내부 2단 구조라 별도로 다뤘다(아래 남은 제한 사항)
- [ ] C2. 팝오버 하나하나의 위치·폭을 직접 손보지는 않았다. 대신 아래 두 가지로 최악의 경우(페이지 전체가 가로로 밀림)만 막았다: 입력창 도구줄을 줄바꿈되게 해 팝오버를 여는 버튼 자체가 화면 오른쪽 끝까지 밀려날 가능성을 줄였고, `body`에 `overflow-x: hidden`을 걸어 어떤 팝오버가 화면 밖으로 나가도 페이지 전체가 옆으로 스크롤되지는 않게 했다. 팝오버가 화면 가장자리에서 잘려 보이는 것 자체는 남은 문제다
- [x] C3. 도구줄에 줄바꿈(`flex-wrap`)을 적용했다. 더보기로 묶는 방식은 하지 않았다 — 375px 폭에서도 실제로는 한 줄에 다 들어가 줄바꿈이 필요한 경우를 보지 못했다
- [x] C4. 코드 블록과 같은 방식으로 표를 감싸는 컴포넌트를 추가했다. 자동 테스트로 스크롤 클래스가 실제로 붙는지 검증했다
- [ ] C5. 개별적으로 확인하지 않았다. 코드상 대부분 `truncate` 처리가 이미 있으나, 화면별로 직접 눈으로 확인하지는 못했다

**완료 기준**: 대표 기기 폭 각각에서 모달·팝오버가 화면 안에 온전히 들어오고, 표가 옆으로 스크롤된다.

- [x] D1. 화면 목록은 세우되, D2에서 실제로 확인한 것은 그중 일부다(아래 검증 결과 참고)
- [x] D2. 빈 대화 화면·사이드바 열기 닫기·Context 패널 열기 닫기·둘의 동시 열림 시도(자동으로 한쪽이 닫히는지)를 375 / 768 / 1280px에서 직접 확인했다. 로그인 화면, 실제 대화 내용이 있는 화면, 각 모달·팝오버는 로그인된 개발 서버 상태·시간 제약으로 직접 열어보지 못했다 — 코드 검토와 기존 패턴과의 일치로만 판단했다(아래 남은 제한 사항)
- [x] D3. 나눴다 — 사이드바를 열 방법이 없던 문제, 사이드바·Context 패널 오버레이 시 배경 조작이 막히지 않던 문제, 고정 폭 모달의 화면 밖 넘침, 터치 기기에서 hover 전용 조작이 불가능하던 문제를 핵심으로 분류했다. 팝오버 개별 위치, 태블릿 2단 레이아웃, 긴 텍스트 말줄임 확인은 보기 문제 또는 다음으로 미뤘다
- [x] D4. 위 핵심 문제 전부를 이번에 고쳤다
- [x] D5. 남은 항목으로 아래에 기록했다

**완료 기준**: D1의 화면 목록 전부를 세 폭에서 확인한 기록이 남고, 핵심 기능을 막는 문제는 모두 해소된다.

## 위험과 미리 정해둘 것

- **사이드바 hover 펼침을 버튼 기반으로 바꾸면 데스크톱에서의 기존 조작감이 달라진다.** 넓은 화면에서는 지금의 hover 방식을 유지하면서 좁은 화면에서만 버튼 방식으로 바꿀지, 아니면 전체를 버튼 방식으로 통일할지 먼저 정해야 한다.
- **이 시점에 0820_08(사이드 채팅 트리)의 탭·그래프 화면이 아직 구현 중이거나 막 끝났을 수 있다.** 그 화면도 이번 점검 대상에 들어가므로, D1 화면 목록을 짤 때 그 문서의 화면 구성을 함께 확인해야 한다.
- **점검 범위가 넓어 시간이 많이 들 수 있다.** 마일스톤 D를 시작하기 전에 대표 기기 폭을 좁혀 우선순위를 정한 뒤 진행한다.

### 남은 제한 사항

- **마일스톤 A2/B5 축소**: 계획했던 모바일/태블릿/데스크톱 3단 구분 대신, 기존 코드에 이미 있던 `lg`(1024px) 기준 하나로 좁음/넓음 2단만 구현했다. 태블릿에서 "사이드바 접힘 + 메인 + Context 2단"을 별도로 보여주는 동작은 하지 않았다.
- **C2 (팝오버 위치)**: 모델 선택·웹 검색·추론 단계 등 개별 팝오버의 위치·폭은 손대지 않았다. `body { overflow-x: hidden }`과 도구줄 줄바꿈으로 페이지 전체가 밀리는 최악의 상황만 막았을 뿐, 팝오버 자체가 화면 가장자리에서 잘려 보일 가능성은 남아 있다.
- **C5 (말줄임 확인)**: 채팅 제목·탭 제목·사이드바 대화명의 말줄임 처리를 화면별로 직접 확인하지 못했다. 코드상 `truncate` 클래스는 대부분 이미 적용돼 있다.
- **D2 (미확인 화면)**: 로그인 화면, API 키·프로필·피드백 모달, 각 팝오버, 실제 대화 내용이 있는 화면(표·코드 포함), 브랜치·사이드채팅 트리 화면은 코드 검토와 기존 패턴 일치로만 판단했고 브라우저로 직접 열어보지 못했다. 이 세션은 이미 로그인된 상태의 개발 서버에 접속했고, 로그아웃해 로그인 화면을 직접 보지는 않았다.
- **B4 확인만 함**: 채팅 탭 바는 기존에 이미 `overflow-x-auto`가 있어 별도로 고치지 않았다. 실제 탭이 여러 개 열린 상태에서 좁은 화면 조작을 직접 시연하지는 못했다.
- **다른 세션과의 동시 작업**: 구현 중 같은 저장소를 고치던 다른 세션이 있었다(`Sidebar.tsx`의 섹션 순서, `index.css`의 색상 값, `chatStore.ts`의 인용 스니펫·`limit` 파라미터, 백엔드 여러 파일). 이 문서의 변경은 그 파일들과 겹치지 않는 부분만 건드렸고, 검증 시점에 그 세션의 변경도 함께 컴파일·테스트를 통과하는지 확인했다.
- **마일스톤 E**: 기획 문서(요구사항정의서·FE기능명세서) 반영 여부는 아직 사용자 확인을 받지 않았다. 이 문서에 잠정으로 적어둔 `REQ-072`는, 같은 시점에 다른 세션이 별도 기능("인용 스니펫")에 이미 `REQ-072`를 붙인 것을 확인했다. 실제로 기획 문서에 반영할 때는 번호가 겹치지 않는 새 번호를 다시 확인해서 써야 한다.
